# Логи приложения

Каждый запуск приложения создаёт отдельную папку в корне:

```text
logs/2026-10-14_13-00-00-123-4520/
  python-requests-<pid>.log
  python-responses-<pid>.log
  python-analysis-<pid>.log
  python-errors-<pid>.log
  python-slow-<pid>.log
  python-runtime-<pid>.log
  java-requests.log
  java-responses.log
  pipeline.log
  orchestrator-runtime.log
  supervisor-runtime.log
  geometry-runtime.log
  positioning-runtime.log
  frontend-requests[-<pid>].log
  frontend-responses[-<pid>].log
  frontend-decisions[-<pid>].log
  frontend-errors[-<pid>].log
  frontend-runtime-<pid>.log
```

Дополнительно Java сохраняет отдельные журналы PLC, освещения, триггеров и запуска процессов. Файлы появляются при запуске соответствующего сервиса. PID в Python и Electron разделяет несколько процессов и их перезапуски.

Общий каталог передаётся переменной `IML_LOG_SESSION_DIR`. Его создаёт Linux supervisor. При прямом запуске Java оркестратор создаёт каталог самостоятельно и передаёт его управляемым сервисам. Перезапуски сервисов внутри одного запуска сохраняют ту же сессию; следующий запуск приложения создаёт новую. Для ручного запуска отдельных сервисов задайте им одинаковый абсолютный `IML_LOG_SESSION_DIR`.

Каждая запись содержит время с миллисекундами. HTTP-запросы и ответы связаны идентификатором; ответы содержат статус и `duration_ms`. Python дополнительно связывает этапы инспекции с текущим запросом и отмечает запросы дольше секунды в `python-slow`. Java сохраняет решения и этапы существующего конвейера в `pipeline.log`. Во фронтенде фиксируются HTTP/WebSocket-команды, ответы, переходы подключения и ошибки. Частые preview-кадры и PLC-телеметрия в журнал WebSocket не записываются. Длительность во фронтенде измеряется до получения HTTP-заголовков; на сервере — до завершения обработки ответа.

HTTP-логи содержат метаданные, без тел запросов/ответов: изображения, multipart, base64 и бинарные данные не копируются ради логирования. Диагностика этапов Python ограничивает размеры строк, списков и словарей, заменяет массивы и бинарные данные описанием. Секретные HTTP-заголовки скрываются.

Запись на диск выполняется асинхронно через ограниченные очереди. При переполнении диагностические записи могут быть пропущены, чтобы не блокировать инспекцию; Python и Electron отмечают пропуски в следующей записи. Файлы ротируются после 10 МБ: Python и Electron сохраняют пять резервных файлов, Java — до десяти. Старые папки сессий автоматически не удаляются.

Electron пишет через IPC; браузер отправляет небольшие пакеты в Java на `/diagnostics/frontend`. Этот endpoint принимает не более 20 записей и 16 КБ за запрос, сохраняет только разрешённые поля метаданных.

Существующие переключатели Python (`ANALIS_SURFACE_FILE_LOGGING`, `ANALIS_SURFACE_DISABLE_FILE_LOG`, `python_detector.file_logging`) продолжают работать. Health-проверки Python по умолчанию исключены; включение — `ANALIS_SURFACE_LOG_HEALTH=1`.

После изменения Java сервисы нужно пересобрать через `bash ./rebuild-and-run.sh`; запускать рабочую инспекцию для проверки логов не требуется.

Флаг `-r` / `--rt-diagnostics` в Linux-скриптах запуска добавляет в ту же
папку сессии `rt-samples.jsonl`, `rt-configuration.jsonl`, `rt-threads.jsonl`,
`rt-kernel.jsonl`, `rt-events.jsonl`. Ошибки самого сборщика — `rt-monitor.log`.
Метрики имеют UTC-время с миллисекундами и монотонную временную метку.
JSONL-файлы ротируются после 10 МБ с пятью резервными файлами.
