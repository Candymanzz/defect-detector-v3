# Диагностика времени инспекции

## Где искать

В Linux-шаблоне `линукс+кресты` — `<корень проекта>/logs/performance/`.
Без явно заданного `integration.performance_log.directory` — `<корень проекта>/cppAnalisSurface/logs/`:

| Файл | Что измеряет |
|---|---|
| `performance-orchestrator-YYYY-MM-DD-<pid>.jsonl` | триггер, камеры, очереди Java, RPC/HTTP, вердикты, запись в ПЛК |
| `performance-detector-YYYY-MM-DD-<pid>.jsonl` | запросы C++, внутренние этапы анализа, heatmap и подготовку/отправку ответа |

Это один диагностический набор в двух файлах: каждый процесс пишет только свой файл. Если запущено несколько
C++-процессов, файлов детектора будет несколько. Для анализа отправлять оба вида файлов за нужный период,
желательно вместе с прежними `cas-*.log`, `inspections-*.jsonl` и журналом оркестратора.

Старые файлы при перезапуске не удаляются. Запись идёт с добавлением; дата в имени и `ts_utc` — UTC.
При смене даты начинается новый файл. Новые performance-файлы автоматически не очищаются: следить за свободным местом.
Существующее логирование и выборка записей в `inspections-*.jsonl` не менялись.

## Включение

В конфигурации оркестратора, блок `integration`:

```yaml
integration:
  performance_log:
    enabled: true
    directory: "cppAnalisSurface/logs"
    queue_capacity: 8192
```

Относительный путь разрешается от корня проекта. По умолчанию диагностика включена даже при отсутствии блока.
`queue_capacity` задаёт размер очереди Java; в C++ очередь ограничена 8192 записями.
При автозапуске C++ оркестратор передаёт ему флаг и каталог. Если C++ запускается отдельно, используются:

- `CAS_PERFORMANCE_LOG=0` — отключить его performance-журнал; иначе включён.
- `CAS_PERFORMANCE_LOG_DIR` — переопределить каталог; по умолчанию рядом с `cas-*.log` (учитывается `--log-dir`).

После пересборки и перезапуска Java в консоли появится `[performance] asynchronous diagnostics directory=...`.
В Java-файле первая запись — `trace_started`; C++ пишет события при получении HTTP-запросов.
Для полного набора полей нужно пересобрать и перезапустить Java, C++-детектор и `camera-worker`.
При отключении через конфиг отдельно запущенный C++ также нужно отключить его переменной окружения.

## Как связаны записи

Каждая строка — отдельный JSON. `cycle_id` объединяет цикл, `trigger_sequence` — номер триггера,
`camera_id` и `frame_id` — камеру и кадр. `request_id` связывает конкретный Java HTTP-вызов с C++;
`parent_request_id` в Java указывает на запрос кадра. `session_id`, `detector_id` и PID различают перезапуски.
Для ручных HTTP-вызовов без Java C++ создаёт свой `request_id` и возвращает его в `X-Request-Id`.

| Событие/поле | Что смотреть |
|---|---|
| `trigger_received` | начало отсчёта; поле `boundary` описывает, где получен триггер |
| `camera_capture_service`, `capture_stage_complete` | время захвата; второе включает ожидание планировщика |
| `camera_capture_response.camera_metrics` | `capture_wait_ns`: SDK/ожидание кадра; `capture_copy_ns`: преобразование/копирование, включая Windows flush |
| `binary_rpc` | очередь транспорта `queue_ms`, вызов `transport_ms`, внутренние `service_metrics`, если сервис их вернул |
| `geometry_stage`, `detector_stage`, `geometry_rpc_complete`, `detector_rpc_complete` | очередь Java/семафора и время выполнения этапа/вызова; отключённая геометрия не считается выполненной инспекцией |
| Java `http_request` | `request_serialize_ms`, `rpc_ms`, `total_ms`, HTTP-статус/ошибка, объём ответа |
| `response_decode` | разбор ответа C++ на стороне Java |
| C++ `http_request_received`, `http_response_prepared`, `http_request` | начало обработки, подготовленный ответ, завершение записи ответа |
| C++ `ms` | `prepare_ms`, `align_ms`, `diff_ms`, `anomaly_ms`, чтение SHM, очереди, heatmap, сериализация и прежнее синхронное логирование |
| `camera_verdict`, `bucket_verdict` | решение отдельной камеры и итог группы; в группе видны обязательные/полученные камеры и тайм-аут |
| `plc_job_complete`, `plc_pulse_hold` | очередь ПЛК и удержание импульса, способное задержать следующую команду |
| `plc_output_confirmed` | ПЛК подтвердил запись значения вердикта по FINS; `write_ms` — длительность обмена |
| `plc_output_failed`, `plc_output_await_failed` | отказ обмена или ожидания; это не подтверждённый выход |
| `plc_output_unchanged` | в режиме удержания уровень уже установлен; новой записи и нового подтверждения не было |
| `plc_bit_write` с `pulse_reset:true` | сброс импульса, а не новый вердикт |

`trigger_elapsed_ms` у `bucket_verdict` — от программного получения триггера до решения группы.
У `plc_output_confirmed` — до подтверждения записи в ПЛК, отдельно для каждой группы.
Завершение `cycle_fanout_complete` само по себе подтверждением ПЛК не является.

## Границы измерений

- Начало — приём UDP-пакета Java перед разбором. Если этот момент недоступен (например, отложенный вызов),
  используется вход в шину триггеров; это явно указано в `trigger_received.boundary`. Это не электрический
  фронт датчика и не начало экспозиции камеры.
- Конец FINS-обмена — ответ ПЛК на запись, не физическое срабатывание отбраковывателя. Текущая ветка
  отправляет вердикт через FINS; нельзя трактовать это как замер прямого DO-выхода.
- Длительности считаются монотонными часами внутри своего процесса. Не вычитать абсолютные часы Java и C++.
- C++ `request_ms` начинается после чтения тела HTTP-запроса, на входе в маршрутизацию, и заканчивается
  после записи ответа библиотекой httplib. Это не подтверждение получения клиентом. Полный клиентский
  обмен, включая транспортные очереди и чтение тела ответа, виден в Java `rpc_ms`.
- `algorithm_ms` включает `prepare_ms`, `align_ms`, `diff_ms`, `anomaly_ms`; `visuals_ms` включает
  `heatmap_render_ms` и `heatmap_write_ms`. Родительские и дочерние таймеры не складывать повторно.
  `accounted_ms` складывает только непересекающиеся верхние этапы, `unaccounted_ms` показывает остаток.
  Если библиотека не вызвала завершение, оно помечается неизвестным, без выдуманного полного времени.

## Нагрузка и ограничения

Новый журнал не выбирает каждый двадцатый кадр: записывает все инструментированные запросы и события.
Изображения, бинарные тела и полные HTTP-тела не сохраняются. Запись файлов и JSON-сериализация журнала
выполняются фоновым потоком; потоки инспекции добавляют компактные записи в ограниченную очередь.
При переполнении диагностика отбрасывает записи, а не ждёт диск. Счётчик — `dropped_records_since_last_write`;
при ошибке записи/суточном лимите выводится сообщение `[performance]` в stderr.

Ограничение — примерно 512 МиБ на UTC-день и PID для каждого вида performance-файла. После достижения
лимита новые записи пропускаются до следующей даты. При пропусках нельзя считать журнал полным.
Не требуется менять пороги брака, позиционирование или алгоритм инспекции ради этих замеров.

## Локальные проверки

Java: `mvn -f orchestrator-java/pom.xml -Dtest=PerformanceTraceTest,PerformancePlcTest,PerformanceHttpCorrelationTest test`.
C++ после обычной CMake-конфигурации с `BUILD_TESTING=ON`:
`cmake --build cppAnalisSurface/build --config Release`, затем
`ctest --test-dir cppAnalisSurface/build -C Release --output-on-failure`.

Тесты используют временные файлы и локальные HTTP/FINS-имитаторы, не камеры и не ПЛК станка.
Они проверяют корреляцию, запись, таймеры и обработку отказов, но не подтверждают лимит 500 мс на реальном железе.
