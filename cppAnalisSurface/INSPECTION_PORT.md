# Перенос логики инспекции из ветки 123

2026-10-28, ветка назначения `ppc-reserv`, исходная версия `d1ac431a`.
Источник вычислительных исправлений: `CppDetector`, ветка `123`, commit `244cea1`.

## Что перенесено

- Одинаковая предобработка эталона/кадра при дробном масштабе, копия одноканального входа перед размытием.
- Дополнение миниатюр и Hann-окна до чётного оптимального DFT-размера. Нулевая оценка смещения на одинаковых входах;
  пересчёт в исходные пиксели использует размер миниатюры до добавления полей. Кеш эталона остаётся неизменяемым.
- Площадь аномалии и min_blob_area считаются по пикселям 8-связной компоненты. Чистые отверстия контуров не закрашиваются.
- Допуски смещения в мм: дробный пересчёт в пиксели, округление конверта один раз на масштабе анализа,
  предел общего смещения равен физическому допуску. Исходные px-поля поддерживаются для совместимости.
- min_contrast стыка применяется в измерении. Ненайденная/неизмеримая линия при включённой проверке даёт брак;
  более ранняя причина брака поверхности сохраняется. ROI с нулевой площадью отклоняется.
- Метрика проходит через существующие настройки/API/Java-оркестратор/React-интерфейс. Идентификатор камеры
  передаётся отдельно от пользовательского имени профиля. При общем сохранении масштаб и калибровка одной камеры
  не копируются на другие камеры.
- Пустой, неизвестный или некорректный ответ инспекции не превращается в ACCEPT в Java-клиенте.

Тестовый интерфейс CppDetector, его эмулятор, локальные профили и кадры не перенесены.

## Формула score из main

По уточнению владельца 2026-10-28 формула перенесена из [Candymanzz/CppDetector, main, 0c03567](https://github.com/Candymanzz/CppDetector/blob/0c035677902201cc8a8e91e6e58aafcadaf08091/src/inspect/inspector.cpp#L98):

```text
score_percent = min(100, 100 * flagged / roi_area * 500)
anomaly_score = score_percent / 100
```

`flagged` — число аномальных пикселей после фильтрации компонент, `roi_area` — число пикселей ROI
на том же масштабе анализа. При нулевой площади score равен нулю. Исходный диапазон main — 0..100;
API и пороги прода используют 0..1, поэтому выполняется деление на 100.
Численно это эквивалентно прежнему `min(1, area_percent / 0.2)`: 0.2% площади ROI дают score=1.
Заводской default threshold остаётся `0.6`. Формула из 123 `/5 * 3` не переносилась.
Обновлены неверные старые подсказки UI и README. Сохранённые пользовательские пороги не переписываются.
Анализ поверхности и стыка остаётся grayscale. Захват, PLC, триггер, Java geometry/positioning и транспорт SHM остаются прежними.

## Миллиметры и миграция

Основные поля: `horizontal_shift_tolerance_mm`, `vertical_shift_tolerance_mm`, диапазон 0..10 мм;
ожидаемый рабочий диапазон 0.5–4 мм. Значения хранятся в профиле и доступны без интерфейса ручной калибровки.

Приблизительные масштабы исходной ветки (мм/пиксель для 1224×1024):

| camera_id | Горизонталь | Вертикаль |
| --- | ---: | ---: |
| 0 | 0.25 | 0.33 |
| 1 | 0.28 | 0.32 |
| 2 | 0.31 | 0.31 |
| 3 | 0.25 | 0.32 |
| 4 | 0.27 | 0.34 |
| 5 | 0.27 | 0.34 |
| 6 | 0.25 | 0.33 |
| 7 | 0.22 | 0.23 |
| 8 | 0.22 | 0.32 |
| 9 | 0.28 | 0.33 |

`mmPerPixelX = estimatedX * 1224 / width`, аналогично Y с 1024/height.
Это компенсация цифрового изменения размеров; оптический масштаб и перспективу надо проверить на машине.
В ответах есть `metric_scale_source=estimated`, `mm_per_pixel`, `shift_mm`, `shift_raw_mm`, `shift_limit_mm`,
`effective_shift_tolerance_mm`, `analysis_pixel_mm`. Эффективный локальный конверт округляется до рабочего пикселя,
поэтому он может отличаться от заданного числа мм; оценка переноса около порога также имеет погрешность.

Например, `PUT /settings/custom-profile?camera_id=4`:

```json
{"horizontal_shift_tolerance_mm":2.0,"vertical_shift_tolerance_mm":1.5}
```

Старые `shift_tolerance`, `shift_tolerance_x/y` читаются. Начальные мм при чтении профиля получаются из legacy-px
на базовом разрешении с масштабом камеры; мигрируемое значение ограничено 10 мм. При сохранении явные мм остаются
каноническими. Временные overrides запроса не записываются в профиль. Некорректное сохранение атомарно отклоняется.
Прямой старый px-override заменяет мм-настройку соответствующей оси только для этого запроса.

Для эмпирического уточнения доступен `estimated_mm_per_pixel:[x,y]` в базовом разрешении. По умолчанию масштаб
не фиксируется в файле при сохранении другого профиля. Также поддерживаются нормализованные измерения `calibration`
с осями `horizontal`/`vertical`, точками p0/p1 и length_mm, как в 123; при обеих валидных осях source=`calibrated`.

## Проверка

- C++: существующие shift/cache/performance тесты и новый inspection_port_test — четыре набора.
- Java: 19 тестов физической диагностики, передачи camera_id через settings proxy, штатных binary headers и агрегатора решений;
  некорректный ответ инспекции проверяется отдельно от штатного отсутствия эталона/CAPTURE.
- Frontend: production build (TypeScript + Vite), 60 тестов, включая независимые мм-поля и исключение
  px/scale metadata из сохранения на все камеры.
- Через настоящий `/upload-ref-shm` → `/inspect-shm`: одинаковый реальный кадр на разрешениях 1×/2×,
  масштабах 1/0.7/0.5/0.2 и допусках 0.5/4 мм; атомарность неверного PUT и сохранение после перезапуска.
- На 1000 кадрах с несколькими масштабами/допусками 0.5–4 мм карты diff, маски, площадь и оценка смещения
  совпали с 123. Score сравнивался с сохранённой формулой прода, а не с другой шкалой 123.

Эти проверки не заменяют разметку реального брака и проверку масштаба/полного цикла на станке.
Известные ограничения малого Downscale и слабоконтрастного стыка остаются в knowledge/known_issues.md.
