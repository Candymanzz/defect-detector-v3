# Оптимизация инспекции, 15.10.2026

Ветка: `optim`. Базовая версия для сравнения: `4616cb7a`.

## Что изменено

1. Добавлен потокобезопасный LRU-кэш подготовки эталона: серый кадр, CLAHE,
   размытие, локальные минимумы/максимумы, градиенты, контуры и данные для
   компенсации освещения. Ключ учитывает содержимое и размер обрабатываемого
   эталона, фактическую ветку CLAHE и необходимость детальной ветки. Поэтому
   новый эталон, масштаб или другой ROI не используют несовместимые данные.
   Ограничение — 128 МиБ и 256 записей на процесс; CV-расчёты выполняются вне
   общей блокировки кэша. Численные правила детекции не менялись.
2. Позиционирование заменено на фазовую корреляцию для небольшого переноса X/Y.
   Рабочий размер — до 640 пикселей по большей стороне ROI с контекстом;
   признаки эталона и окно кэшируются. Проверяются уверенность, ограничение
   сдвига 32 пикселя в исходном разрешении и улучшение совмещения. При
   ненадёжной оценке исходный кадр продолжает обычную инспекцию: это не
   принудительный «ГОДЕН» и не технический «БРАК».
   Удалены ORB/RANSAC из этого позиционирования, поиск поворота, повторные
   полноразмерные уточнения, маски void/dropped, подстановка пикселей эталона
   и зануление карты различий по полосам позиционирования. Выполняется один
   итоговый перенос кадра; выходящие за изображение края продолжаются
   ближайшими пикселями текущего кадра (`BORDER_REPLICATE`). Содержимое за
   границами снимка восстановить невозможно, поэтому ROI должен находиться
   внутри кадра с запасом на колебание.
3. Общая блокировка ORB для оставшихся старых/FP-путей не изменена.
   Число процессов и инспекционных потоков также не изменялось.
4. Оркестратор по умолчанию отправляет `defer_learning_review: true`, в том
   числе при отсутствии настройки в старом конфиге. Явное `false` сохраняет
   синхронный режим. Параметр добавлен в `config.exemple/blocks/20-detectors.yaml`.
   Сохранение истории остаётся ограниченной best-effort очередью; переполнение
   логируется и не меняет вердикт. Задержка 250 мс отсчитывается от постановки
   кадра, а не добавляется заново перед каждой записью в накопленной очереди.
   Тепловая карта не занимает инспекционный пул: используется отдельный поток,
   максимум четыре незавершённых задачи на процесс, ожидание до трёх секунд.
   Запись истории и построение карты делят один фоновый слот и ждут завершения
   уже поставленных/работающих инспекций и паузы 25 мс. Начатая фоновая операция
   не прерывается, но новая инспекция её блокировку не ждёт.
   При перегрузке визуализация отвечает HTTP 429; Java уже обрабатывает такую
   ошибку как отсутствие вспомогательной карты, без изменения вердикта.

## Измерение скорости

`frames36`: десять камер, кадр 387 используется как эталон каждой камеры,
390 — прогрев, 391–395 — пять измеряемых пакетов по десять камер.
Масштаб инспекции 0,75; порог 0,45. Четыре Python-процесса по три потока;
OpenCV однопоточный. Все процессы ограничены одними четырьмя **логическими**
CPU этой рабочей станции. Это имитация ограничения CPU, не измерение на
четырёхъядерном компьютере станка. Кадры декодируются до начала измерения.
Настройки операторских ROI/FP/обученной нормы для этого набора не предоставлены:
использованы отдельные тестовые профили без таких зон. OpenVINO-модель локально
отсутствует, работает обычный алгоритмический детектор.

| Обработка пакета из 10 камер только в Python | Среднее, мс | Максимум, мс |
| --- | ---: | ---: |
| До изменений, повторный базовый прогон | 1441,54 | 1506,00 |
| После изменений, отложенная история | 768,44 | 852,96 |

Среднее сократилось на **46,69%**. Первый независимый прогон дал 1386,76 →
756,72 мс, то есть результат повторяется. В повторном прогоне среднее время
позиционирования на камеру под конкурентной нагрузкой: 455,25 → 115,87 мс;
расчёта различий: 514,43 → 465,79 мс. Это перекрывающиеся времена отдельных
вызовов, их нельзя складывать для получения времени пакета.

Замер **не включает** триггер, захват камер, Java, HTTP, передачу в PLC,
построение UI-карт и завершение записи истории. Поэтому достижение 600 мс
от триггера до физического выхода не подтверждено. Главный оставшийся
вычислительный расход Python — расчёт различий и фильтрация их свидетельств.

Результаты повторного прогона:

## Корректность и ограничения

- 374 Python-теста пройдены; 13 пропущены (платформенные/отсутствующие изображения).
  Добавлены проверки кэша, переноса, сохранения нового дефекта, отсутствия
  подстановок/масок, приоритета инспекции, отмены запросов и перегрузки карт.
- На 100 сравнений карт различий с исходной реализацией, получавшей те же
  выровненные пиксели, результаты совпали побитово. Это изолированная проверка
  кэширования, а не заявление об идентичности нового позиционирования старому.
- На 40 заданных переносах реальных эталонов всех десяти камер совмещение
  каждый раз улучшилось. Максимальная ошибка определения переноса — 0,34 пикселя.
- В обычном прогоне 50 кадров **пять решений изменились**: раньше 40 «ГОДЕН» /
  10 «БРАК», теперь 39 / 11. Кэширование само по себе это не вызывает; изменены
  геометрическое совмещение и поведение краёв.

| Камера / кадр | До, score | После, score |
| --- | --- | --- |
| 3 / 391 | ГОДЕН, 0,003 | БРАК, 1,000 |
| 0 / 394 | ГОДЕН, 0,446 | БРАК, 0,499 |
| 1 / 394 | БРАК, 0,717 | ГОДЕН, 0,382 |
| 3 / 394 | БРАК, 0,509 | ГОДЕН, 0,219 |
| 6 / 395 | ГОДЕН, 0,383 | БРАК, 0,548 |

В частности, для камеры 3 / кадра 391 прежний алгоритм применял также поворот
примерно 0,21°. Новый намеренно его не компенсирует. Поэтому обещать отсутствие
ухудшений на кадрах с поворотом нельзя. Без разметки неизвестно, какие из
изменившихся решений верны. Для малых **переносов** проверка положительная;
компенсация вращения и изгибов этикетки не входит в эту реализацию.

Java-тест добавлен для нового значения по умолчанию и явного `false`, но
здесь не запускался: Maven и JDK 17 в доступном окружении не обнаружены.
Изменение Java ограничено значением по умолчанию одного существующего поля.
Перед эксплуатацией нужна сборка и проверка на станке с реальными ROI,
частотой триггеров и измерением до выхода на отбраковыватель.
