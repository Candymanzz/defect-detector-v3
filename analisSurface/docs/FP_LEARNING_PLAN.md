# План: дообучение на ложных срабатываниях

Живой документ: текущее состояние, решения и открытые вопросы.
Обновлять по ходу обсуждения, не размазывать по чатам.

---

## 1. Зачем

Оператор не должен рисовать полигон «исключить область».
Он говорит: этот БРАК был ложным → система запоминает куски diff
и на следующих кадрах той же камеры отличает знакомый ложняк от нового дефекта.

Контракт:

- уже отправленный на конвейер вердикт **не переигрывается**;
- обучение влияет только на **следующие** инспекции этой же сессии;
- норма привязана к камере и текущему эталону;
- после перезапуска Python отмеченные ложняки **можно и нужно терять**:
  свет, установка, эталон к этому моменту уже другие, старые куски вредны.

---

## 2. Как сейчас

Параллельно живут две системы.

### 2.1 Старые FP-зоны (прод-фронт)

- Оператор рисует полигон в `FpZoneEditor`.
- Фронт → WS `client.fp_zones_update` → оркестратор `replace_fp_zones` → Python `POST /fp-zones`.
- На inspect полигон **всегда вырезается** из diff/маски (hard exclude).
- Ключ: `product_type`, оркестратор скоупит как `bucket#cam=2`.
- Предложений координат нет: зона только руками.

### 2.2 Learned normals (Python)

Документы: `docs/LEARNED_NORMALS.md`, `backend/docs/LEARNED_NORMALS_API.md`.

На каждом inspect:

1. обычный diff vs основной эталон;
2. маска режется на компоненты (`extract_defect_candidates`);
3. каждая сравнивается с сохранёнными нормами того же `product_type` + `reference_hash`;
4. совпадение рядом (центры ≤ 15% кадра) → каскад кропа (погасить / цветовой остаток);
5. потом ещё старые FP-зоны;
6. если итог любой — кадр кладётся в историю на диск (`inspection_id` UUID, FIFO 50).

Оператор жмёт **одну кнопку** «Дообучить этот БРАК»:

`POST /learning/reviews/{inspection_id}/accept-all-as-normal`

Либо по-прежнему выбирает один контур:

`POST /learning/reviews/{inspection_id}/defects/{defect_id}/accept-as-normal`

Координаты уже есть: `bbox`, `bbox_norm`, `polygon`. UI этого — страницы Python
(`/learning-review`, `/local-inspection-test`), не основной React.

Нормы пишутся на диск `backend/app/data/accepted_normals/` **только на время
процесса**. На старте каталог очищается. После рестарта ложняки не действуют.

### 2.3 Камеры

В проде Python видит `product_type = "{product}#cam={N}"`.
Норма камеры 0 не применяется к камере 1.
Смена эталона меняет `reference_hash` → старые нормы сами перестают матчиться.

`inspection_id` Python (UUID review) ≠ `inspection_id` Java (цикл конвейера).

## 3. Целевой UX: кнопка «дообучить»

Не выбирать фрагменты руками. Оператор жмёт одну кнопку на кадре,
который считает ложным БРАКом.

Поток:

1. На фронт/оркестратор есть `inspection_id` из ответа inspect.
2. На Python уходит этот id. `product_type` **можно не слать** — он уже в review.
3. Python берёт сохранённый diff/маску этого inspect, нарезает куски ложняка
   (те же кандидаты, что уже посчитаны).
4. Каждый кусок сохраняется как accepted-case со своим `id` (удаление по одному).
5. Следующие инспекции этой камеры применяют каскад (раздел 4).

Смысл кнопки: «весь этот БРАК был ложным».
Если на кадре ложняк **и** настоящий дефект — кнопка выучит оба. Это единственный
жёсткий риск. Advanced-режим «принять один контур» оставить.

Мелочь в UI можно не сохранять (`filter_review_candidates`), как сейчас.

Черновик API:

```http
POST /learning/reviews/{inspection_id}/accept-all-as-normal
```

Тело опционально: `{ "note": "блик этикетки" }`.
Ответ: список созданных `accepted_case.id`.

## 4. Механика следующих инспекций: каскад, не второй inspect

**Не делать** вторую полную инспекцию кадра. Дорого и незачем.

Каскад по кропу:

```
весь кадр vs основной эталон
  вне известных мест → обычный вердикт
  рядом с сохранённым ложняком:
    1) кроп кадра vs кроп основного эталона
    2) тихо → зона ОК, мини-эталон не трогаем
    3) сработало → тот же кроп vs мини-эталон ложняка
         низкий score → ложное срабатывание (погасить)
         высокий score → реальный дефект поверх ложняка (брак)
```

Сравнивать в пространстве **diff** (+ форма маски), не сырой RGB.
Искать не по всему кадру, а в окне вокруг исходного места (~15% как сейчас).

Это лучше текущего «похоже → вырезать»: новый скол на знакомом блике должен остаться браком.

## 5. Хранение: диск в сессии, пусто после рестарта

Два разных слоя, не путать.

| Слой | Что это | Нужен после рестарта? |
|---|---|---|
| Review / diffmap | кадр БРАКа, чтобы нажать «дообучить» | нет |
| Accepted FP | уже отмеченные куски ложняка | **нет** |

Почему нормы не живут между запусками: после рестарта условия другие
(свет, геометрия, эталон, даже пыль на объективе). Вчерашний блик как
мини-эталон сегодня даст ложный suppress настоящего брака.

Сейчас `accepted_normals/` как раз переживает рестарт — это лишнее.
Либо чистить каталог на старте, либо держать нормы только в RAM/temp
текущего процесса.

### Review / diffmap

`InspectionReviewStore` пишет кадры БРАКа на диск, в RAM только индекс:

```text
backend/app/data/learning_reviews/{inspection_id}/
  meta.json          # product_type, reference_hash, score, status, created_at
  aligned.jpg
  diff.png
  mask.png
  heatmap.jpg
  defects.npz        # шаблоны контуров для accept-all
```

Правила:

- писать каждую инспекцию (`ГОДЕН` и `БРАК`);
- лёгкий индекс в RAM, картинки и шаблоны с диска;
- лимит 50 внутри сессии (FIFO overwrite), `ANALIS_LEARNING_REVIEW_LIMIT`;
- на старте сервиса каталоги `learning_reviews/` и `accepted_normals/` очищать;
- `product_type` в meta обязателен (`#cam=N`).

## 6. Стыковка с продом (ещё не сделано)

Гайд для оркестратора и React: `docs/FP_LEARNING_INTEGRATION.md`.

Коротко:

- оркестратор проксирует learning API (как `/fp-zones`) и отдаёт Python UUID
  отдельным полем `learned_review_id`, не подменяя Java `inspection_id`;
- в карточке БРАКа: кнопка «дообучить» + список сохранённых норм этой камеры;
- фильтр всегда `product_type = "{product}#cam={N}"`;
- старые FP-зоны пока не удаляем: hard exclude остаётся запасным инструментом.
