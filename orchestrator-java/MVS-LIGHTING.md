# Встроенный свет MVS

Java управляет Ethernet MV-LE и COM MV-LE через JNA и MvCameraControl.
LightServer.v3 больше не запускается оркестратором, launcher или скриптами сборки;
его исходники сохранены для сравнения. .NET для света не требуется.

## Настройка

Конфигурация читается из основного YAML с импортами:

- `config/blocks/50-lighting.yaml`: `light_servers.enabled`, `backend: native`,
  путь SDK, таймауты, очередь команд, переподключение, имена GenICam-узлов,
  яркость и режим света.
- `config/blocks/51-light-hardware.yaml`: IP/COM/serial устройств, каналы и
  маршруты `camera_number` → `device_id`/`channels`. Номер камеры = id + 1.
  Один канал соответствует single, два — pair; режим выводится из маршрута.
- `interval_flash` в конфиге света управляет On/Off по DI2; постоянный режим
  и сохранение яркости через существующий API оркестратора сохранены.

В репозитории находится `config.exemple`; рабочий каталог `config` должен
содержать настройки реальных устройств. На Linux обязательно заполните
`com_port_linux` для COM-вспышки. Принимаются `/dev/ttyUSB0`, `ttyUSB0` и
`COM_Port#ttyUSB0`: SDK получает последний формат. Не указывайте здесь
`COM_Port#ttyS4`, если это порт MV-VC IO-контроллера.
Неиспользуемые устройства отключите через `enabled: false` и удалите их маршруты.
Управление ограничено явно перечисленными каналами; чужие камеры и MV-VC
не принимаются как устройства света.

Linux: 64-битная JVM и установленный SDK `/opt/MVS/lib/64/libMvCameraControl.so`.
Windows: 64-битная JVM; библиотека и зависимости в
`orchestrator-java/native/mvs/win64/`. IO и свет должны использовать одну и ту же
библиотеку SDK. Для Linux нужны права на последовательный порт и сеть устройств.

## Выполнение

На каждый контроллер создаётся постоянная native-сессия и один поток с
ограниченной очередью команд. Очередь сериализует обращения к SDK одного
устройства; это не очередь аппаратных триггеров камеры. Bank On/Off отправляет
команды разным устройствам параллельно. Если контроллер поддерживает All,
он используется только когда конфиг включает все его реальные каналы.
Иначе команда выполняется по каналам.

Яркость задаётся без включения света. Перед последующим On изменённая яркость
применяется с Off, как в прежней реализации. Режимы capture/DI/constant используют
существующий LightTriggerClient. Аппаратная цепочка камеры и таймеры MV-VC
не перенастраиваются этим модулем.

Обрыв связи переводит устройство в ошибку и запускает переподключение.
После переподключения восстанавливается яркость, каналы остаются Off; нужен
новый On от режима управления. Health gate видит отказ встроенного света.
При штатном закрытии выполняются Off и CloseDevice. Initialize/Finalize SDK
разделяются со встроенным IO через счётчик пользователей: выключение света
не финализирует библиотеку работающего IO.

Таймаут ограничивает ожидание команды и удаляет просроченные команды очереди.
Вызов, уже выполняющийся внутри vendor SDK, Java прервать не может; это не
гарантия жёсткого реального времени. SIGKILL также не позволяет выполнить Off.

## API и журналы

Все запросы — на порту оркестратора (по умолчанию 8099):

- GET `/api/orchestrator/light/bank`: готовность, ошибки устройств.
- POST `/api/orchestrator/light/bank`: `{"state":"on"}` или `{"state":"off"}`.
- GET `/api/orchestrator/light/devices`, `/api/orchestrator/light/com/devices`:
  настроенные устройства и их состояние.
- Существующие API изменения яркости и постоянного режима сохранены.
- `/api/camera-flash/pair`, `/single`, `/bank`, `/routes` доступны на том же порту;
  pair/single меняют яркость по настроенным маршрутам.

`logs/light-module.log` содержит соединения, SDK-вызовы, ошибки и закрытие;
`logs/lighting.log` — решения режимов подсветки.

Модуль покрыт тестами с подменёнными устройствами: маршруты, яркость без On,
параллельный bank, переподключение, Off при закрытии и совместная жизнь SDK с IO.
Физические вспышки и полный цикл с камерами после переноса ещё не проверены.

## Изменяемые параметры

В `50-lighting.yaml` теперь явно заданы:

- `sdk.health_check_ms`, `worker_poll_ms`, `reconnect_ms`, `command_timeout_ms`,
  `queue_size`, `shutdown_timeout_ms`: интервалы и ограничения native-модуля.
- `sdk.initial_brightness`: начальная яркость 0..255 (каналы при соединении Off).
- `sdk.source_on`, `source_off`: символы SDK; в YAML строки `"On"` и `"Off"`
  обязательно заключайте в кавычки. Устройство может переопределить их.
- `sdk.use_broadcast`, `broadcast_selectors`, `refresh_before_on`: использование
  All и обновление изменённой яркости через Off перед On.
- `sdk.open_access_mode`, `switchover_key`: параметры открытия SDK.
- `runtime.command_attempts`, `retry_delay_ms`: повторы On/Off в клиенте.
- `runtime.startup_poll_ms`, `status_timeout_ms`: ожидание готовности.
- `brightness_store_path`: файл сохранённых яркостей относительно корня проекта;
  абсолютный путь тоже допустим.
- `default_camera_mode`: режим для совместимого HTTP-конфига без маршрутов.

В `51-light-hardware.yaml` для каждого устройства настраиваются `model_prefixes`,
`brightness_min`, `brightness_max`, а также необязательные `source_on/source_off`.
Яркость API 0..255 переводится в заданный диапазон SDK; интерфейс остаётся в %.
IP, COM, serial и каналы также задаются здесь. Никаких специальных id камер 2/7
или ограничения id до 9 в выборе света больше нет. Маршруты определяют,
каким камерам принадлежит свет; остальные камеры не получают команды света.

Размеры C-структур, смещения полей, коды транспортов SDK и формат API — часть
протокола, а не параметры установки; они остаются в коде. Значения по умолчанию
сохранены для старых конфигов, параметры установки можно переопределять без сборки.
