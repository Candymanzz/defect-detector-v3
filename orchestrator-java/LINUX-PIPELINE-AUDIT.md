## Исправлено в ходе проверки

`LightServer.v3/Services/MvsComPortEnumerator.cs` теперь нормализует
`COM_Port#ttyS4`, `ttyS4`, `/dev/ttyUSB0` без удвоения префикса SDK
и без изменения регистра Linux-имени. Windows COM-имена сохраняют прежнее
поведение. Добавлены случаи в xUnit-тесты; семь вариантов отдельно проверены
на собранном LightServer через reflection без обращения к оборудованию.
Полный xUnit-набор не запускался: его зависимости ещё не восстановлены.

SHM-тест Python предполагал Windows-путь, хотя выполнялся на Linux.
Его Windows-окружение теперь явно задаётся локально в тестируемом модуле;
производственный `shm_io.py` не изменён. После этого полный набор Python
без integration проходит. Первоначальное зависание FastAPI-тестов было
устранено запуском вне ограничений песочницы.

## Что препятствует утверждению «можно запускать линию»

1. В checkout отсутствует рабочий каталог `config`. Запуск ожидает
   `config/config.yaml`, camera-worker — `config/config.json`, LightServer —
   `config/blocks/51-light-hardware.yaml`. Есть только `config.exemple`.
   Перед запуском нужны рабочие файлы с реальными IP, портами и маршрутами;
   один `CONFIG=config.exemple/config.yaml` не меняет путь JSON камеры
   и конфигурацию LightServer автоматически.
2. Шаблон COM-вспышек содержит `COM1`. На Linux нужно указать реальное имя
   порта вспышек из SDK, например `ttyUSB0` или `COM_Port#ttyUSB0`.
   Это не должно занимать serial-порт IO-контроллера одновременно с Java.
3. При последнем сравнении Timer5 был `Software`, Burst, 6 секунд, delay 600 мкс;
   Out5 связан с Timer5. Для заявленной рабочей цепочки нужен источник In3
   и подходящие длительность/задержка, настроенные в MVS. Java Timer5 не меняет.
4. `poll_ms: 1` — пауза между обменами, а не период получения DI.
   Предыдущая аппаратная проверка двух DI дала примерно 41 мс на скан.
   Во время команды Timer6/7 чтение DI ждёт тот же synchronized SDK-handle.
   Короткие импульсы и два события с интервалом 80 мс могут быть пропущены;
   отсутствие debounce не устраняет пропуски опроса.
5. Camera-worker очищает SDK-буфер перед `wait_frame`, как запрошено.
   Если аппаратный кадр уже пришёл к этому моменту, он может быть удалён,
   после чего worker получит следующий аппаратный кадр либо timeout.
   Задержки In3→Timer5, DI-опроса, IPC и GigE должны быть измерены вместе.
6. DI2→вспышки управляется отдельной очередью и HTTP. DI3 не ждёт подтверждения,
   что вспышки реально включились. Для экспозиции свет должен успеть включиться
   до аппаратного фронта камеры. `hold_mode: true` не включает свет при capture.
7. Ошибки настройки TriggerMode/TriggerSource камеры в C worker местами
   игнорируются. Успешный старт процесса сам по себе не доказывает правильную
   аппаратную настройку камеры: проверять SDK-логи и фактические кадры.

## До аппаратного прогона

Из корня репозитория используйте `source tools/env.sh`: локальные Java/.NET
не установлены в системном PATH. Рабочий запуск — `bash ./run-rt.sh` либо
`bash ./run-supervised.sh` после подготовки рабочего `config`.

На оборудовании нужно подтвердить: DI2 включает свет до экспозиции;
In3 запускает Timer5 и кадр на каждой камере; кадр относится к нужной детали;
короткие/повторные DI3 не теряются, в том числе при браке Timer6/7;
FAIL даёт импульс на нужном входе Omron, остальные сигналы идут по FINS;
потеря связи и повторное подключение не создают лишнего триггера.
Измерять физические сигналы вместе с `logs/io-module.log` и журналом стадий.
