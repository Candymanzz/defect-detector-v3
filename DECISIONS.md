# Архитектурные решения

Журнал сложных решений при сведении веток `36-to-30` (станок на **4 изделия**, машина 30) и `core-dev`
(станки на **2 изделия**). Новое решение — новым разделом `D-NNN`, спорное — в «Открытые вопросы».

Статус: `принято` · `требует проверки на станке` · `отложено`.

## Контекст

- Общий предок веток: `edf87948` (2026-08-19). С тех пор `core-dev` +131 коммит, `36-to-30` +28.
- `core-dev` новее и считается основой. Но `36-to-30` менял пайплайн под 4 изделия за 2 фазы (два DI3 на цикл),
  и эти изменения терять нельзя.
- Принцип: **различия между станками — в конфиге**; где в конфиг не выносится (разная логика) — выбор реализации
  по значению из конфига, а не отдельная ветка.

## D-001. Выдача вёдер (изделий) на ПЛК/UI: `fanout_mode`

**Статус:** принято, **требует проверки на станке 30 и на станке на 2 изделия** (код не компилировался, см. OQ-1).

**Проблема.** `BucketInspectionAggregator` в ветках делает противоположные вещи:

| | `core-dev` (2 изделия) | `36-to-30` (4 изделия) |
|---|---|---|
| Выдача | Ждёт все ведра одного `triggerSequence` и шлёт пакетом (`reject_line_1` и `reject_line_2` синхронно) | Каждое ведро сразу, независимо от соседа и фазы |
| Нет соседнего ведра | Через `timeout_ms` синтетический брак линии | Ничего не придумываем |
| Ключ ведра | `(triggerSequence, groupId)` | `(parentCycleId, phaseId, groupId)` |
| Ранний брак ручки | Есть | Нет |
| capture-only ведро | Публикуется как годное | Не публикуется |

Для 4 изделий барьер по `triggerSequence` не подходит: ведра фаз 0 и 1 приходят на разных триггерах
(второй DI3 через ~80 мс), и ждать «всех» значило бы либо блокировать фазу 1, либо слать синтетический брак.

**Решение.** Один класс, ключ ведра фазовый (для одной фазы он совпадает со старым), режим выбирается конфигом:

```yaml
integration:
  inspection_bucket:
    fanout_mode: sequence_barrier   # по умолчанию, станки на 2 изделия
    # fanout_mode: immediate        # станок на 4 изделия (машина 30)
```

| Поведение | `sequence_barrier` | `immediate` |
|---|---|---|
| Барьер по циклу (внутри одной фазы) | да | нет |
| Синтетический брак за отсутствующее ведро | да | нет |

Два спорных места **не привязаны к режиму**, а вынесены в отдельные флаги (см. D-005).

Не зависят от режима и перенесены из `core-dev` для обоих: soft-stop (`PerCameraInspectionGate`: остановленная
камера не обязательна для ведра), `reevaluateOpenBucketsAfterGateChange`, порядок «сначала ПЛК, потом UI»
(`afterPlcUi`), расширенные логи. Фазовые перегрузки `recordFrameResult` сохранены.

**Реализация.**
- `pipeline/bucket/BucketFanOutMode.java` — enum и разбор значения.
- `BucketInspectionConfig` — новое поле `fanOutMode`; 4-аргументный конструктор оставлен (режим по умолчанию
  `SEQUENCE_BARRIER`), чтобы не ломать существующие вызовы и тесты.
- `BucketInspectionAggregator` — объединённая версия. Барьер ключуется по `(parentCycleId, phaseId)` и ждёт
  группы **только своей фазы**.
- `BucketInspectionAggregatorTest` — тесты `core-dev` как есть (режим по умолчанию) + тесты `36-to-30`
  с явным `BucketFanOutMode.IMMEDIATE`.

**Почему режим, а не «взять новое».** Вторая сторона тоже обоснована: барьер гарантирует синхронный сигнал
на ПЛК по двум линиям, а немедленная выдача — независимость изделий. Выбор зависит от того, как станок
подключён к ПЛК, поэтому он принадлежит конфигу станка.

## D-005. Спорное не объединяем, а выносим в переключатель

**Статус:** принято. Принцип: пока непонятно, общая это логика или свойство станка, **ничего не сливаем и
не выбираем победителя** — оставляем оба поведения и включаем одно из них в конфиге. Что можно объединить,
решим после того, как программы будут сведены и проверены на станках.

Флаги в `integration.inspection_bucket` (если не заданы, берутся из `fanout_mode`, т.е. прежнее поведение ветки):

| Флаг | По умолчанию `sequence_barrier` | По умолчанию `immediate` | Что делает |
|---|---|---|---|
| `early_reject` | `true` | `false` | Первый бракованный кадр сразу пишет бит брака **во все** линии ПЛК, не дожидаясь остальных кадров. Работает только при `plasticHandleMode` (регистр ПЛК `D4405` ≠ 0). Появился в `core-dev` (`5b4b7f45`) |
| `suppress_capture_only` | `false` | `true` | Ведро, где все кадры сняты **без эталона** (`CAPTURE`), не публикуется. При `false` такое ведро уходит на ПЛК как **годное**. Появился в `36-to-30` (`3c51d8db`, «фиксы для 30й») |

Реализация: `BucketInspectionConfig.earlyReject()` / `suppressCaptureOnly()`; примеры в обоих наборах конфигов
выставлены явно.

Аналогично: `analysis_settings.json` — настройки детектора станка (порог 1.0 против 0.3, `min_defect_area` 50 против 12,
CLAHE выключен и т.д.). `core-dev` не хранит его в git. Версия `36-to-30` закоммичена в ветке; решение,
где ему жить, отложено.

## D-002. `PerCameraInspectionGate`: объединение без выбора

**Статус:** принято.

Правки сторон не пересекаются по смыслу, поэтому слиты обе:
- из `core-dev`: `systemBlocked` (vision_fault), `snapshotInspectionEnabled`/`restoreInspectionEnabled`,
  `suppressSoftStopPreview`;
- из `36-to-30`: учёт фаз in-flight (`PhaseKey`), `awaitPriorPhase`, `requestCancelAllInFlight(keepPhase1)`,
  `endInspection(camera, parentCycleId, phaseId)`.

Для одной фазы (`phaseId=0`) поведение совпадает со старым.

## D-006. Триггеры и цикл инспекции

**Статус:** принято, не компилировалось (OQ-1).

**`IoInputMonitorUdpTriggerTransport`** — основа `36-to-30` (двухфазный DI3, окно DI2, `arm_on_direction`),
плюс единственное изменение `core-dev`: съёмка разрешена, только если физическое направление DI2
**совпадает с выбранным в UI «Прямой/Обратный»** (`directionMatchesSelected()`, раньше UI не фильтровал).
Это меняет, когда станок снимает, поэтому вынесено в флаг:

```yaml
integration:
  inspection_trigger:
    io_input:
      direction_must_match_selected: true   # 2 изделия (core-dev); false — 4 изделия (UI не фильтрует)
```

Поле `IoInputDiscreteConfig.directionMustMatchSelected`, по умолчанию `true`. Если ключа нет в рабочем конфиге
станка на 4 изделия, поведение изменится — выставьте `false` явно (в `config.exemple.4-products` это сделано).

**`InspectionTriggerBus`** — объединены обе стороны: фазовая диагностика `TwoPhaseCaptureDiagnostics` и
`dispatchLineBroadcast(..., phaseId, parentCycleId, rawTriggerSequence)` (`36-to-30`) + гейт
`setDispatchAllowed` (не принимать триггеры, пока сервисы нездоровы) и `clearAllPending` (`core-dev`).
Гейт проверяется в основном методе диспетча, поэтому действует и для фаз.

**`AsyncInspectionCycleRunner`** — взята схема `core-dev`: UI-часть оформлена как `publishUi` и отдаётся
агрегатору (`afterPlcUi`, сначала ПЛК, потом UI); без агрегатора выполняется сразу. Из `36-to-30` оставлено:
UI получает кадр с идентичностью цикла (`withCycleIdentity`: фаза и parent cycle), а не «сырой»
`state.capture()`.

## D-007. Импульсы ПЛК (`PlcFinsPublisher`): `pulse_threads`

**Статус:** принято, не компилировалось (OQ-1). Критично для железа — проверить на обоих станках.

| | `core-dev` | `36-to-30` |
|---|---|---|
| Импульс reject | в потоке публикатора, последовательно; длительность отсчитывается от момента записи `true`; `awaitEdge` ждёт подтверждения фронта; режим «ручка» держит reject до PASS | пул потоков `pulse_threads`, замок на сигнал: импульсы разных линий идут параллельно |

Объединено: `PulseBitJob(signal, active, pulseMs, future)`, семантика фронта/`awaitEdge`/`holdRejectUntilPass` и
таймингов из `core-dev`; исполнение выбирается конфигом `plc_fins.pulse_threads`:
`1` (по умолчанию, **изменено с 4**) — как `core-dev`; `>1` — параллельный пул `36-to-30`
(в `config.exemple.4-products` выставлено `4`). Если в рабочем конфиге станка 30 ключа нет, он перейдёт на
последовательные импульсы — выставьте `pulse_threads: 4`.

## D-008. Прочие объединения Java

**Статус:** принято, не компилировалось.

- **`PipelineCameraRuntimeService` / параллелизм.** Взят фикс `core-dev`: семафор python-запросов =
  `python_request_parallelism`, а не число URL серверов. По умолчанию он равен `python_server_pool_size`; на
  станке 30 это 2 вместо 20 и сериализует камеры, поэтому в `config.exemple.4-products` выставлено
  `python_request_parallelism: 20`. Без этого ключа на станке 30 будет регресс по скорости.
- **`CriticalServiceWatchdog`.** Взят механизм перезапуска `core-dev` (счётчик неудач, `restartNotBeforeMs`,
  восстановление). Простой 2-секундный backoff из `36-to-30` удалён как дублирующий. Сохранён фикс `36-to-30`:
  при рестарте python поднимается `python_server_pool_size` серверов, а не по числу HTTP-клиентов.
- **`InspectGeometryExecutor`.** Проверка «нет эталона → пропустить» стоит **до** позиционирования (`core-dev`),
  в `36-to-30` — после. Взят порядок `core-dev` (защита от `null` эталона); позиционирование без эталона не выполняется.
- **`InspectPythonExecutor`.** Оба: выбор python-сервера по фазе (`selectPython`, `36-to-30`) и применение
  `analysis_profile`/runtime overrides (`core-dev`).
- **`AnalisSurfaceHttpBinaryRpcSupervisor`.** Тело запроса — объединение полей (`camera_id/frame_id/phase_id` и
  `roi_polygon_norm`, `analysis_test_settings` и т.д.).
- **`ReferenceBundleParser`.** Конфликт был только из-за концов строк (CRLF/LF); трёхсторонний мерж прошёл без
  конфликтов: фаза/группа эталона (`36-to-30`) + линия перспективы (`core-dev`).
- **`UiTestAnalyzeService`.** Взята версия `core-dev` (изолированный SHM, pin-кадры тестового анализа);
  рефакторинг `getPipelineState` из `36-to-30` ничего не добавлял.
- **`FrameArchiveService.SaveRequest`.** Поля фазы/группы (`36-to-30`) + `learnedReviewId`, размер кадра
  (`core-dev`); конструкторы на 10/11/13 аргументов оставлены для вызовов обеих сторон.
- **`UiArtifactsSidecar`.** Взята версия `core-dev` целиком. Перенесено из `36-to-30`: `phase_id` в запрос
  heatmap и `phase_id`/`group_id` в архив кадра. **Не перенесено** — см. OQ-7.

## D-009. `IoInputMonitor` (C#, генерация DO5): два переключателя

**Статус:** принято, C# не собирался.

Основа — `core-dev`. Две его логики вынесены в `io_input` (`blocks/52-io-input.yaml`), потому что станок на 4
изделия работает иначе (два DI3 за одно окно DI2 — две фазы):

| Ключ | `core-dev` / 2 изделия | 4 изделия | Что делает |
|---|---|---|---|
| `direction_must_match_selected` | `true` (по умолчанию) | `false` | DO5 только если физическое DI2 совпадает с выбранным в UI «Прямой/Обратный»; смена направления сбрасывает окно и перевооружает. При `false` считается только DI2 |
| `one_capture_per_di2_window` | `true` (по умолчанию) | `false` | Один DI3 на окно DI2=1, повторные холостые. При `false` каждый DI3↑ при DI2=1 снимается |

С обоими `false` поведение совпадает с `36-to-30`. Для оркестратора есть парный флаг
`inspection_trigger.io_input.direction_must_match_selected` (D-006) — выставляйте их согласованно.

## D-010. Python `analisSurface`

**Статус:** принято; синтаксис проверен, `pytest` не запускался (не установлен).

- **Позиционирование только в Java.** `core-dev` убрал выравнивание из Python (`_use_fixed_frame`, тест
  `test_inspection_never_runs_python_positioning`). `36-to-30` ещё выравнивал в Python (ORB/ECC) и замерял остаточный
  сдвиг. Взята модель `core-dev`: оба примера конфига включают `java_positioning`. **Если на станке
  позиционирование выключено, Python больше не выровняет кадр.**
- **Диагностический вердикт-лог (`36-to-30`) перенесён.** Строка `inspect_verdict` (причины брака, остаточный сдвиг
  `pose_gap`, статистики карт) пишется в `logs/python-inspect.log`; теперь она **включается тем же флагом
  `python_detector.file_logging`**, что и остальные логи. Поля `camera_id`, `frame_id`, `phase_id`, `shm_name`
  принимаются в `ShmFrameRequest` и `inspect_frame`.
- **HTTP-лог.** Две независимые реализации; взят модуль `core-dev` (`app/file_logging.py`), тот же ключ в
  конфиге. Встроенный лог из `main.py` и переменная `ANALIS_SURFACE_HTTP_LOG` убраны.

- `referenceImages.ts`: хранилище эталонов по слоту (фаза/группа/камера) + архив с именем и наследованием «доп. кадров»

- `ReferenceController`/`ReferenceSetup`: вкладки по вёдрам, архив и текущий эталон фильтруются по фазе/группе.

- `App.tsx`, `App.css`, `AnalysisSettingsPanel`, `orchestratorApi`, типы — `core-dev` (в `.app-header` оставлен

## D-012. Кадр эталона из окна: `ui_http.stable_reference_frame` (закрывает OQ-7)

**Статус:** принято, на станке не проверено. Причина: в окне эталона на станке 30 сервер отвечал
`kopcheni_sync_failed: ... reference shm not found: /iml_line_pin_cam0_f131`.

`UiArtifactsSidecar` (версия `core-dev`) сразу после публикации в UI освобождает line-pin кадра, а окно эталона
позже присылает именно его имя — файла уже нет. В `36-to-30` пин не освобождался (его чистит janitor по TTL 45 с,
оставляя 2 последних на камеру), а в UI/WS уходило имя замороженной копии `iml_ui_inspect_cam_N`.

Ключ `ui_http.stable_reference_frame`: `false` (по умолчанию, `core-dev`) — освобождать сразу; `true` (4 изделия) —
вернуть поведение `36-to-30`. **Нужно выставить `true` в рабочем конфиге станка 30.**
Риск: замороженная копия — одно имя на камеру, перезаписывается следующим кадром (в т.ч. другой фазы) за ~80 мс;
это поведение `36-to-30`, дальнейшее усиление (уникальное имя на фазу) — отдельная задача.

## Открытые вопросы

- **OQ-1. Код не компилировался и тесты не запускались.** На этой машине нет JDK/Maven (только Java 8 JRE),
  а в дереве ещё есть конфликты в других файлах. Агрегатор, гейт, конфиг и тесты — только по чтению. Первый
  шаг после мержа: `mvn -f orchestrator-java test`.
- **OQ-2. `suppress_capture_only`.** Что должен показывать станок без эталона на камерах: «ничего» (30)
  или «годно» (`core-dev`)? Пока — флаг в конфиге (D-005). Вопрос к автору `core-dev` / технологу.
- **OQ-3. `early_reject`.** Есть ли на машине 30 режим пластиковой ручки (регистр `D4405`) и должен ли он
  браковать все линии сразу? В 4-изделийном варианте это значило бы брак всех 4 изделий, включая ещё не снятые
  фазы, — потребуется привязка к линиям/фазе. Пока флаг `false` для `immediate`.
- **OQ-4. Барьер при нескольких фазах.** В `sequence_barrier` он ждёт группы своей фазы. Комбинация
  «несколько фаз + барьер» не проверялась и не поддерживается по замыслу.
- **OQ-5 (закрыт).** `GeometryTestSettingsPanel.tsx` и `TestSettingsPanels.css` оставлены из `core-dev`.
