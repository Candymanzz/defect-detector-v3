# Логи трёх сервисов инспекции

После сборки и запуска оркестратора каждый запуск создаёт каталог:

```text
logs/service-traces/ГГГГ-ММ-ДД_ЧЧ-ММ-СС_мс/
├─ session.txt
├─ pipeline-stages.jsonl
├─ java-positioning/
│  ├─ rpc-<pid>.jsonl
│  └─ java-positioning-<номер>/positioning-runtime.log
├─ java-geometry/
│  ├─ rpc-<pid>.jsonl
│  └─ java-geometry-<номер>/geometry-runtime.log
└─ analisSurface/
   └─ worker-<pid>-<время>/
      ├─ http.jsonl
      ├─ requests.log
      ├─ responses.log
      ├─ analysis.log
      ├─ errors.log
      └─ slow.log
```

`rpc-*.jsonl` и `http.jsonl` содержат по одной JSON-записи на событие. Поле `request_id` связывает запрос с ответом или ошибкой в пределах одного процесса. `timestamp` содержит дату, время и часовой пояс. В ответе есть `duration_ms`, статус и заголовок/тело ответа. Поля `camera_id` и `frame_id`, если они пришли в запросе, позволяют сопоставить сервисы с `pipeline-stages.jsonl`.

Бинарные кадры и большие встроенные изображения в логи не копируются: записываются размер данных и остальные поля ответа. В Python обычный JSON сохраняется до 64 КБ на запись, очень длинные строковые значения заменяются отметкой с их длиной. Заголовки авторизации и cookie скрываются. Это ограничивает размер журнала на непрерывном станке.

Для проверки производительности нужен запуск **собранных заново** JAR-файлов оркестратора, `java-positioning-service` и `java-geometry-service`, а также актуального Python backend. Скрипт `rebuild-and-run.ps1` собирает все три Java-модуля. При запуске другой копии проекта каталог появится в `logs/service-traces` именно той копии.

Для анализа передайте целиком одну папку сеанса с указанным временем. Сравнение `duration_ms` показывает время внутри сервиса; `pipeline-stages.jsonl` дополнительно показывает ожидание в очереди, захват кадра, решение и общее время цикла. Логи могут содержать пути к файлам и параметры производства — передавайте их только доверенному получателю.
