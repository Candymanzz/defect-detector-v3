# Накопительная статистика инспекций за запуск

Дата **2026-11-09**, ветка `boobs+pasha`, исходный HEAD `a120fe68`.
Владелец уточнил: сохранять статистику после перезапуска программы не требуется;
если начинается новый отсчёт кадров, статистика тоже начинается заново.
Нужна отдельная кнопка сброса.

## Поведение

- «Всего», «Год» и «Брак» по группам накапливаются независимо от количества
  сохраняемых кадров, в том числе при лимите 0. Изменение лимита, удаление фотографий
  и обрезка экранной истории не уменьшают счётчики.
- Панель подписана «за запуск». «Сбросить статистику» обнуляет только счётчики;
  инспекция, эталон, архив и настройки детектора не сбрасываются.
- При новом запуске/перезагрузке frontend счётчики изначально равны нулю.
  При наблюдаемом перезапуске счётчика capture/preview начинается новая генерация;
  последовательные сбросы нескольких камер не обнуляют её повторно.
- Считаются производственные `server.inspect_result` и `server.inspect_bucket_result`.
  Несколько камер с одним `inspection_id` — одна инспекция в своей группе.
  Общий итог объединяет одинаковый ID двух групп, как прежде.
- Итоговый вердикт bucket имеет приоритет над промежуточными вердиктами камер.
  Это позволяет учесть групповой REJECT, даже если он появился после per-camera PASS.
  Повторные сообщения и отложенный heatmap не увеличивают «Всего» повторно.
- TEST-перепроверки, CAPTURE и NO_REFERENCE не добавляют производственных инспекций.
  Начальная загрузка последнего сохранённого снимка не восстанавливает старую статистику.

## Реализация и причины

Ранее `inspectionStatsByCameraId` хранила полные `InspectionHistoryItem[]`;
`trimInspectionStatsItems` обрезала их до `inspectionHistoryLimit`. Счётчики
пересчитывались по оставшимся элементам и упирались в лимит архива.

Новый [InspectionStatistics](../../front-end/src/components/MainOverview/inspectionStatistics.ts)
поддерживает числовые счётчики инкрементально, независимо от истории изображений.
На ID инспекции хранятся только битовые признаки PASS/FAIL камер и окончательных
вердиктов двух групп. Полные payload, пути фотографий, heatmap и learning-данные
в статистике не удерживаются. Обновление не обходит всю историю инспекций.

Для точного распознавания повторов сохраняются компактные ID всех инспекций текущего
запуска: память этой таблицы растёт с числом уникальных инспекций, но не с размером
payload. Произвольное окно последних N ID не выбрано: очень поздний повтор старого
результата иначе увеличил бы счётчик второй раз. Ручной сброс оставляет старые ID
без вердиктов, чтобы позднее сообщение не восстановило обнулённую статистику.
Новая генерация кадров/перезапуск frontend очищает таблицу полностью.

[useInspectionStatistics](../../front-end/src/components/MainOverview/useInspectionStatistics.ts)
подписан на WS отдельно от просмотра карточек и их ограниченной истории.
Кнопка панели через `App → MainOverview` передаёт версию ручного сброса.
Существующий «Сброс инспекции» и кнопки Stop/Start не вызывают этот отдельный сброс.
Время «Старт»/«Стоп» сохраняет прежний смысл управления инспекцией.

## Границы

Счётчики относятся к наблюдаемым WS-результатам текущего запуска frontend.
Они не ведутся на сервере и не восстанавливают пропущенные во время закрытия UI
или разрыва WS инспекции. Это не постоянный производственный журнал.
Автоматический сброс внутри открытого UI определяется снижением capture/preview
`frame_id` при неубывающем серверном времени. Отдельного server-instance ID в
текущем протоколе нет; если после перезапуска backend новых preview-событий нет,
доступен явный сброс кнопкой.

Оборудование, реальный производственный поток и перезапуск backend не проверялись;
Java/C++ не изменялись, runtime не перезапускался, commit/push не выполнялись.
