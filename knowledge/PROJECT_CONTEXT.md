# Контекст проекта для нового ИИ-агента

Срез: **2026-10-28 · `ppc-reserv`**, основа `d1ac431a`, вычислительные исправления из `CppDetector/123` (`244cea1`). [Навигация](README.md). [Состав переноса](../cppAnalisSurface/INSPECTION_PORT.md).

## Продукт и задача

Инспекция этикеток на вёдрах реального станка, до 10 камер. Нужно находить дефекты этикетки, удерживая минимум ложного брака на колебаниях ведра и изменениях съёмки. Оператор может отключать отдельные камеры; решение должно учитывать обязательные камеры соответствующей группы.

**Требование владельца:** целевой предел **500 мс от триггера до выдачи результата на отбраковыватель**. В старой переписке фигурировали 600 мс; актуальный целевой бюджет — 500 мс. Локальный ответ C++ за 83 мс не доказывает выполнение полного бюджета.

**Со слов владельца:** производственная машина имеет **6 ядер и RT-окружение**. Фактические CPU affinity, SMT, изоляция IRQ, ядро и политики потоков на станке в последнем тесте не проверялись. Не использовать устаревшее предположение о четырёх ядрах и не считать все ядра выделенными приложению.

## Что работает в этой версии

- Детектор поверхности — **`cppAnalisSurface`, C++/OpenCV**, если `python_detector.backend: cpp`, как в шаблоне конфигурации.
- Java-оркестратор получает триггер, организует захват и RPC, агрегирует вердикты, работает с UI и отправляет результат в PLC по FINS.
- Нативный захват реализован в **`camera-worker` на C**, с SDK камеры. Не переносить сюда описание другой ветки о захвате внутри JVM без проверки.
- Frontend — `front-end`, React/TypeScript. Управляет эталонами, ROI и настройками, показывает результаты и карты различий.
- `IoInputMonitor` и `LightServer.v3` обслуживают аппаратный ввод/вывод и освещение. `DI3` — текущий триггер съёмки в шаблоне; `DI1`/`DI2` участвуют в разрешении работы/направлении.
- Старые Python, Java geometry и Java positioning **сохранились в репозитории**. Их наличие не означает, что они включены в конкретном запуске. Нельзя писать «все остальные сервисы вырезаны».

## Принятые решения

1. Позиционирование поверхности компенсирует небольшой **перенос X/Y**. Проворот этикетки, поворот/перспективу и удаление полос сейчас не добавлять ради компенсации колебаний.
2. Основные настройки — `horizontal_shift_tolerance_mm` и `vertical_shift_tolerance_mm`, допуск сравнения и предел общего переноса в мм. Масштабы камер пока приблизительные из 123; их нужно уточнить на машине. Старые px-поля читаются для совместимости. Это не полная геометрическая проверка положения этикетки относительно поверхности ведра.
3. Кэш эталона должен быть неизменяемым. В `bfd9b54a` перед `phaseCorrelate` добавлена рабочая копия миниатюры; устранён ложный брак, накапливавшийся при повторах.
4. Приоритет — быстрый вердикт. `defer_heatmap: true` позволяет формировать карту после основного ответа, но фоновые запросы всё равно могут конкурировать за CPU и рабочие слоты.
5. В UI есть обновление кадров эталона с сохранением ROI. Это отдельное действие; полная замена эталона может сбрасывать редактируемые зоны.
6. В C++ нет дообучения, обученных норм и FP-перепроверки старого Python. Их прежние оптимизации не описывают текущий горячий путь.
7. Score сохраняет продовую формулу `min(1, area_percent/0.2)` и default threshold=0.6. Шкала `/5*3` из тестового проекта не переносилась. Площадь теперь считает реальные пиксели связных компонент, не закрашивая чистые отверстия.
8. Исправлен ложный полупиксельный ноль phaseCorrelate. Включённый ненайденный стык даёт брак. Неизвестный/неполный ответ детектора в Java не считается ACCEPT.

## Важные текущие числа

| Параметр | Значение и источник |
|---|---|
| C++ workers | В шаблоне автозапуска 12; у отдельного процесса без аргумента — число логических CPU, с ограничением 1–64 |
| Клиентская параллельность | В шаблоне `server_concurrency: 10`, один сервер C++ |
| OpenCV | Внутри процесса задан `cv::setNumThreads(1)`; параллельность организована между запросами |
| Настройки по умолчанию | sensitivity 0.5, threshold 0.6, камера 0: горизонталь 0.75 мм / вертикаль 0.99 мм (приблизительно), min_blob_area 20 px², inspect_scale 1.0 |
| Шкала score | 100% оценки соответствует 0.2% отмеченной площади ROI; это не 100% площади и не вероятность брака |
| Локальный замер | 20 505 запросов; ошибок/тайм-аутов нет, все клиентские запросы короче 500 мс |
| 10 камер, 12 потоков | 1500 измеренных пакетов: среднее 83.1 мс, p99 115.7 мс, максимум 163.7 мс |

Исторический стенд замера 2026-10-27: **Windows, Ryzen 5 5600GT, 6 физических / 12 логических CPU**, `frames36`, масштаб 100%, без настоящего захвата и PLC. [Полная методика](performance/2026-10-27-speed-stability.md). Эти числа не являются повторным замером нового переноса.

## Что ещё не решено

- **Критично:** Java-клиент может принять HTTP 200 с пустым/неизвестным вердиктом за `ok=true`, что при пропущенной геометрии даёт `ACCEPT`.
- В UI остались подсказка о 5% площади вместо 0.2% и резервный threshold 0.25 вместо серверного 0.6.
- В C++ sensitivity=0 **не отключает всю отбраковку**: это минимальная чувствительность пиксельного порога. Старый контракт Python «0 → всегда ГОДЕН» сюда не переносить.
- Полный цикл триггер → подтверждённая запись PLC за 500 мс и физическое срабатывание механизма ещё не подтверждены последними локальными тестами.
- Допуски шва и положения этикетки в мм — отдельное [требование геометрии](geometry/customer_requirements.md), не выполненное самим разделением X/Y.

Перед изменением поведения сверять [детектор](analis-surface/overview.md), [известные проблемы](known_issues.md), код и рабочую конфигурацию. Не выдавать предположение, старую ветку или короткий локальный тест за подтверждённое поведение станка.
