# Причина увеличения времени: ECC и исполнение на одном CPU — 2026-11-11

Продолжение после выбора варианта1: [CPU-слоты реализованы и проверены](2026-11-11-inspection-cpu-slots.md),
бинарник подготовлен, активный сервис ещё не перезапущен. Указания ниже
«код не менялся» относятся к исходному этапу аудита, до реализации.

## Главный результат

Продолжение [разбора рабочих циклов](2026-11-11-reject-latency.md) по запросу
владельца проверить код и объяснить регрессию скорости. Checkout `boobs+pasha`,
HEAD `ebdf115b`; прежние изменения рабочей директории сохранены.

**Подтверждена ошибка сочетания запуска и RT-изоляции:** Java/C++ разрешены
CPU `2-5,8-11`, но автоматическая балансировка на них отключена параметром
ядра `isolcpus=domain`. В проверенном десятисекундном интервале (снимок10:46:15 +03) все потоки
Java/C++ имели последним CPU2; другие изолированные CPU простаивали.
Простой `taskset` с общей маской не обеспечивает распределение между ними.

Отдельный эксперимент на этой машине воспроизвёл поведение: четыре потока
ECC с унаследованной маской выполняются на CPU2; явное назначение каждому
потоку собственного физического CPU ускорило пакет десяти камер с386 до131 мс.
Математика ECC, изображения и критерий сходимости в этом сравнении одинаковы.
Это замер ECC на сохранённых JPEG, **не полный цикл станка и не его дедлайн**.

Вторая часть роста нагрузки — добавленное ранее ECC-уточнение после phase256.
Вместе они дают большой хвост: более дорогие запросы конкурируют на одном
CPU, занимают четыре логических слота сервиса и задерживают остальные камеры.

## Проверка настоящего процесса, а не только исходников

Read-only чтение `/proc` снаружи sandbox, без смены affinity/приоритетов/сервиса:

- C++ PID36256, SHA256 `/proc/36256/exe`:
  `a01e732620adda6fe1e0cf317fa492eb8aeaf098df510a1f7b5ee0802890f67a`.
  Совпадает с `cppAnalisSurface/build/cpp_analis_surface` и build-linux.
- Сборка Release, `-O3 -DNDEBUG ... -O2`, не Debug. Эффективно последняя
  опция оптимизации O2; наличие O3 раньше неё не доказывает O3.
- C++ environment `ANALIS_INSPECT_WORKERS=4`;66 потоков, все last_cpu=2.
  Из них23 получили более1 мс CPU за окно; у всех last_cpu=2.
- Java PID36205,254 потока в последнем замере, все last_cpu=2;
 90 активных по тому же критерию — также CPU2.
- Общая разрешённая маска у обоих процессов и проверенных потоков2-5,8-11.
  Политика проверенных активных потоков SCHED_OTHER, nice0.
- Топология:2/8,3/9,4/10,5/11 — SMT-пары четырёх физических ядер.
  Это не восемь физических ядер.
- Ядро `6.8.1-1015-realtime`, cmdline содержит:
  `isolcpus=domain,managed_irq,2-5,8-11 nohz_full=2-5,8-11`.
  `/sys/devices/system/cpu/isolated` подтверждает2-5,8-11.
- В предыдущем десятисекундном чтении `/proc/stat` CPU3-5 и8-11 имели
  нулевую активность и100% idle. Из изолированного набора работал CPU2.
- Например, в сохранённом десятисекундном замере один поток C++ получил
  108.9 мс CPU и337.4 мс ожидания runqueue; другой64.8 мс CPU и268.4 мс
  ожидания. Это не стоимость математических операций. Runqueue-счётчик
  относится ко всем задачам потока в окне, не отдельно к конкретному ECC.

`isolcpus=domain` исключает CPU из обычной балансировки планировщика;
размещение на них нужно организовывать явно. Это соответствует
[документации параметров ядра Linux](https://cdn.kernel.org/doc/html/latest/admin-guide/kernel-parameters.html).
`nohz_full` и RT-ядро сами по себе не распределяют вычислительные потоки.

Загружены приватные OpenCV core/imgproc/imgcodecs4.6.0 и системный video4.6.0;
BLAS/LAPACK — обычные системные, OpenBLAS не обнаружен. Ошибка размещения
воспроизводится с теми же OpenCV-библиотеками. Доказательств, что именно
смешивание библиотек вызвало регрессию, нет.

## Что изменилось относительно быстрых замеров

В commit `37499f9e` от2026-11-05 появился ECC после phase256. Ранее этой
итерационной стадии не было. В `663ee885` от2026-11-06 добавлена компенсация
исходного BGR перед повторным gray/blur. Это разумные изменения для точности
и подавления артефактов, но вычислительная стоимость выше.

Контрольные хвостовые выборки старых рабочих файлов:
2026-11-03 — align13.3 мс;2026-11-05 —15.2;2026-11-06 —13.3.
Сегодняшняя основная выборка —206.5 мс. Это разные кадры/версии/конфигурации,
поэтому отношение не является контролируемым тестом одной правки.
В проверенных performance-файлах за9–10 ноября записей `/inspect-shm`
не найдено; они не дают соседнего рабочего сравнения до/после пересборки.
Backup бинарника перед пересборкой10 ноября уже содержит findTransformECC:
нельзя объявлять10 ноября точной датой первого появления ECC в runtime.
Изоляция/общая маска тоже не доказаны как новые именно сегодня.

## Как исправлять

**Первый шаг — явное размещение вычислителей, с сохранением алгоритма.**
Правильное место в C++ — выдача вычислительного слота (`Service::Slot`) или
отдельные вычислительные workers. Каждому одновременно занятому слоту нужен
конкретный CPU; общая маска не заменяет это при `isolcpus=domain`.
Назначать нужно физические ядра, учитывая SMT, и резервировать CPU для
Java/захвата/IO. Один вариант для испытания — C++ на3/4/5, Java/IO на2,
с числом вычислителей по фактически выделенным ядрам. Эта конкретная схема
ещё не измерена; проверенное сравнение выше использовало2/3/4/5 для C++ probe.

Не достаточно увеличить inspect_workers с4 до10: без размещения все они
продолжат конкурировать на CPU2. Не достаточно повторить `taskset -apc`
с той же общей маской: это по-прежнему не балансировщик isolated CPU.
Разовая ручная миграция потоков также не решает создание новых после restart.

Альтернатива — вернуть обычную балансировку через изменение boot/cpuset
архитектуры. Она затрагивает всю RT-настройку машины и не выбрана как
первый шаг. Изменения GRUB и перезагрузка здесь не выполнялись.

**Второй шаг — измерить полный пакет и только затем оптимизировать ECC.**
Нужны отдельные phase/ECC/warp wall+thread-CPU таймеры и регрессия на тех же
изображениях с известными переносами и настоящим браком. Снижение числа
итераций/ослабление epsilon возможно, но меняет измерение сдвига и требует
проверки. Известный риск ECC при изменении яркости остаётся:
[предыдущая валидация](../analis-surface/2026-11-05-ecc512-prepush-validation.md).
Карты можно вынести после вердикта; это вторичный резерв примерно10 мс
в среднем, не самостоятельное устранение нынешнего хвоста.

В этой задаче подготовлены диагностика и проверяемые варианты исправления.
Исходники приложения, runtime YAML, systemd, affinity и приоритеты рабочих
процессов не менялись; сборка/установка/перезапуск приложения не выполнялись.
Подтверждение полного предела500 мс после исправления остаётся открытым.
