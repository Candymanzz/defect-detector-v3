## 1. Что реализовать в интерфейсе

В настройках выбранной камеры добавить редактор «Зоны исключения инспекции».
Пользователь рисует замкнутый многоугольник **на эталоне**, затем сохраняет его.
Можно добавить несколько зон, удалить выбранную, удалить все. Удобный набор
действий: «Нарисовать зону», «Убрать точку», «Сохранить зону», «Отмена».
Сохранённые зоны стоит показывать полупрозрачной розовой заливкой и контуром.

Внутри зон **безусловно не проверяются отличия поверхности**; соответствующие
сечения шва тоже пропускаются. Новые реальные дефекты внутри зоны также будут
игнорироваться. Это отличается от «Дообучить», где новый дефект в обученном
фрагменте продолжает сравниваться. Действующие ROI и обученные нормы — отдельные
настройки; не редактируйте их для реализации исключений.

Снаружи зон поверхность и шов продолжают проверяться. Score считается по
оставшейся площади ROI. Если вся ROI поверхности исключена, её score равен 0
даже при sensitivity=1. Проверка шва вне исключённых участков и отдельная
Java-геометрия могут при этом дать брак. Исключения не отключают камеру и PLC.

## 2. Формат данных и координаты

```ts
type ExclusionPoint = [number, number];
type ExclusionPolygon = ExclusionPoint[];
type Exclusions = ExclusionPolygon[];

type InspectionExclusions = {
  polygons: Exclusions;
  coordinate_space: "normalized";
  surface_skipped: boolean;
  remaining_area_work_px: number;
};
```

Поле настроек называется **`exclusions`**. Оно содержит массив многоугольников,
а каждый многоугольник — массив точек `[x, y]`. Координаты нормализованы в **0..1**:
`[0,0]` — верхний левый угол эталона, `[1,1]` — нижний правый. Обратите внимание:
это пары чисел, а не объекты `{x,y}` существующего ROI API.

Для точек в исходных пикселях эталона размера W×H:

```ts
const xNorm = xPixel / (W - 1);
const yNorm = yPixel / (H - 1);
const xPixel = xNorm * (W - 1);
const yPixel = yNorm * (H - 1);
```

Учитывайте реальные границы картинки, `object-fit`/поля, масштабирование и pan.
Не делите экранные координаты на весь контейнер, если картинка занимает его часть.
Редактор работает в координатах эталона; поверх сырого непозиционированного кадра
контуры нельзя просто нарисовать без преобразования. Если нужны контуры поверх
результата, используйте изображение в координатах эталона. Downscale инспекции
не меняет нормализованные координаты зон.

Ограничения сервера:

- от 0 до 32 зон; от 3 до 128 точек в каждой зоне;
- только конечные числа в диапазоне 0..1, включая границы;
- многоугольник должен иметь ненулевую площадь;
- `[]` означает отсутствие зон; `null` не является способом очистки;
- перекрывающиеся зоны объединяются; отдельные ID, имена и `enabled` у зон
  сервером не хранятся. Поддержку самопересекающихся контуров в UI не предлагайте.

Оставляйте небольшой запас вокруг исключаемого объекта: сравнение использует
размытие. Шов пропускает **целое поперечное сечение**, если его полоса поиска
пересекает исключение; пропуск касается и аппроксимации, и coverage шва.

## 3. Читать настройки камеры

Frontend обращается к Java-оркестратору, как при работе с прочими настройками
детектора. Все URL ниже относительны к его HTTP origin.

```http
GET /api/orchestrator/detector-settings/camera/0
```

Ответ **200**, JSON:

```json
{
  "analysis_profile": "camera-0",
  "settings": {
    "exclusions": []
  },
  "defaults": {
    "exclusions": []
  },
  "saved": false,
  "detector_id": "cpp-analis-surface-example"
}
```

Здесь и далее ответы настроек **сокращены**: реальные `settings` и `defaults`
также содержат все существующие поля детектора — sensitivity, threshold, seam,
inspect_scale, learning и метрические настройки. Не удаляйте их из своих типов.
`analysis_profile` берётся из конфигурации камеры: пример `camera-0` не задаёт
реальное имя профиля вашего запуска. Пользуйтесь URL `/camera/{id}`, не угадывайте
имя. `saved` означает наличие сохранённого профиля целиком, а не наличие зон.

## 4. Сохранить одну или несколько зон

Это **частичное обновление настроек**, но поле `exclusions` заменяет **весь список
зон**. Прочие настройки при таком запросе сохраняются.

```http
PUT /api/orchestrator/detector-settings/camera/0
Content-Type: application/json
```

```json
{
  "exclusions": [
    [[0.2, 0.3], [0.4, 0.3], [0.4, 0.6], [0.2, 0.6]],
    [[0.7, 0.1], [0.8, 0.1], [0.75, 0.2]]
  ]
}
```

Ответ **200**, JSON:

```json
{
  "analysis_profile": "camera-0",
  "settings": {
    "exclusions": [
      [[0.2, 0.3], [0.4, 0.3], [0.4, 0.6], [0.2, 0.6]],
      [[0.7, 0.1], [0.8, 0.1], [0.75, 0.2]]
    ]
  },
  "defaults": {"exclusions": []},
  "saved": true,
  "detector_id": "cpp-analis-surface-example"
}
```

После 200 используйте **`response.settings.exclusions`** как подтверждённое
сервером состояние. Сохранение само по себе не запускает повторную инспекцию.
Настройка применяется при чтении профиля следующей инспекцией; уже начавшийся
запрос продолжает работать со своим снимком настроек.

Зоны сохраняются в C++ `data-dir/settings.json` по `analysis_profile` и переживают
перезапуск. Они не привязаны к fingerprint эталона, как образцы нормы: смена
эталона и его разрешения сохраняет нормализованные зоны профиля. Покажите их
оператору на новом эталоне для проверки расположения. Если две камеры намеренно
используют один `analysis_profile`, они разделяют эти настройки, включая зоны.

## 5. Удаление и сохранение остальных настроек

Удаление одной зоны: удалите её из локальной копии массива и отправьте оставшийся
список тем же PUT. Отдельного DELETE по ID зоны нет.

Удаление всех зон:

```http
PUT /api/orchestrator/detector-settings/camera/0
Content-Type: application/json
```

```json
{"exclusions": []}
```

Ответ **200** — обычный envelope настроек: `settings.exclusions=[]`, `saved=true`.
Не используйте для этого `DELETE /api/orchestrator/detector-settings/camera/0`:
он сбрасывает **весь профиль**, включая пороги, seam, learning и зоны.

При сохранении другого параметра без поля `exclusions` зоны сохраняются:

```json
{"threshold": 0.6}
```

Default нового и старого профиля без поля — `exclusions=[]`. Нет необходимости
записывать пустой массив только из-за открытия страницы.

## 6. Ошибки

Неверная форма/координаты/количество точек при сохранении: **400**, например:

```json
{
  "detail": "exclusion polygon must contain 3..128 points",
  "error_code": "bad_settings",
  "detector_id": "cpp-analis-surface-example"
}
```

Другие тексты `detail`: `exclusions must be an array of up to 32 polygons`,
`exclusion point must be [x, y]`, `exclusion coordinates must be finite numbers in 0..1`,
`exclusion polygon has no area`. Весь невалидный PUT отклоняется: прежние зоны
и прочие настройки этого запроса остаются неизменными.

Прокси также может вернуть **404** для ненастроенной камеры, **503** для
отсутствующего backend URL, **502** для недоступного C++ сервиса. Эти ошибки
могут иметь Java-формат `{"error":"..."}`. В UI читайте `detail ?? error`,
не рассчитывайте на `error_code` у каждого ответа.

При ошибке сохраняйте черновик и показывайте сообщение; серверное состояние
не подменяйте несохранённым. При сетевом таймауте результат PUT может быть
неизвестен: перечитайте GET перед дальнейшими действиями.

## 7. Временно проверить зоны без сохранения

Для основного тестового окна используется существующий асинхронный API.
Сначала должен быть загружен эталон и включён TEST-режим:

```http
POST /api/client/mode/test
Content-Type: application/json
```

```json
{"enabled": true}
```

Затем, например, проверить архивный кадр с черновиком зон:

```http
POST /api/client/inspection/test-analyze
Content-Type: application/json
```

```json
{
  "cameraId": 0,
  "source": "archive",
  "frameId": 42,
  "temporarySettings": {
    "analysis": {
      "settings": {
        "exclusions": [
          [[0.2, 0.3], [0.4, 0.3], [0.4, 0.6], [0.2, 0.6]]
        ]
      }
    }
  }
}
```

Важно сохранить вложенность **`temporarySettings.analysis.settings.exclusions`**.
Это временный список для одного запуска; `settings.json` не меняется.
Передайте `exclusions: []`, чтобы проверить кадр без сохранённых исключений.
Если поле отсутствует, используется сохранённый список профиля.

Ответ **202** подтверждает постановку задания, а не результат анализа:

```json
{
  "ok": true,
  "jobId": "example-job-id",
  "cameraId": 0,
  "frameId": 42,
  "pinId": "example-pin-id",
  "pinJpegSha256": "example-sha256"
}
```

Сам результат приходит обычным `server.inspect_result`. Не меняйте производственный
вердикт или PLC на стороне frontend. Существующие ошибки TEST API сохраняются:
например 409 без TEST-режима, 503 при неготовом сервисе. Невалидное временное
поле `exclusions` C++ отклоняет с 400/`bad_request`; в асинхронном TEST-пути это
уже ошибка анализа, а не гарантированно синхронный HTTP 400 запроса постановки.

## 8. Результат в WebSocket и архиве

В **`server.inspect_result.payload`** добавлено поле **`inspection_exclusions`**:

```json
{
  "type": "server.inspect_result",
  "payload": {
    "camera_id": 0,
    "frame_id": "42",
    "overall_pass": true,
    "action": "ACCEPT",
    "anomaly_score": 0.0,
    "inspection_exclusions": {
      "polygons": [
        [[0.2, 0.3], [0.4, 0.3], [0.4, 0.6], [0.2, 0.6]]
      ],
      "coordinate_space": "normalized",
      "surface_skipped": false,
      "remaining_area_work_px": 100000.0
    }
  }
}
```

WS-пример сокращён: существующие `protocol_version`, `message_id`, кадр, heatmap,
детектор и прочие поля сохраняются. `anomaly_score` — существующая шкала 0..1.

`polygons` — зоны **именно этой инспекции**, включая временные overrides;
не подставляйте сюда текущие настройки редактора. `surface_skipped=true`
означает, что вся ROI поверхности исключена. `remaining_area_work_px` — число
проверяемых пикселей **рабочего масштаба**, не исходная площадь и не число
аномалий. При отсутствии зон новый backend всё равно отправляет объект с
`polygons=[]`. В старых записях/Python-пути поле может отсутствовать: UI должен
это допускать, не объявляя старый результат полностью исключённым.

Такой же объект хранится в архивном `result.json` и выдаётся в каждом элементе
`frames[]` ответа:

```http
GET /api/frame-archive/cameras/0/history
GET /api/frame-archive/cameras/0/frames/42/result.json
```

Первый ответ имеет envelope `{"camera_id":0,"max_frames_per_camera":...,"frames":[...]}`;
во втором `inspection_exclusions` расположен в корне JSON результата. URL
артефактов также доступны в существующих полях истории `result_url`/`frame_url`.
История показывает маску своего кадра даже после редактирования профиля.
Отложенная heatmap также формируется с первоначальным списком зон кадра.

## 9. Рекомендуемый порядок реализации и проверка UI

1. При выборе камеры загрузить GET настроек и сделать отдельную копию списка зон.
2. Рисовать на эталоне отдельным слоем. Действия рисования не должны менять ROI,
   seam или текущие образцы нормы. Отмена/смена камеры сбрасывает только черновик.
3. Локально проверять количество точек, диапазоны и ненулевую площадь. Серверная
   валидация остаётся обязательной. До сохранения можно запускать TEST с черновиком.
4. Сохранять весь список одним PUT, блокируя повторное сохранение до ответа.
   У API нет revision/ETag: не запускайте конкурирующие PUT одного списка и
   не отправляйте устаревшие копии настроек из другой формы.
5. Связывать ответ с камерой, для которой был отправлен запрос: если пользователь
   переключился во время запроса, не заменять им редактор другой камеры.
6. После успеха предложить повторную проверку кадра. Статус «сохранено» не означает,
   что уже показанный результат был пересчитан.
7. Проверить: добавление нескольких зон; удаление одной/всех; cancel/undo;
   ошибка PUT и повтор; переключение камер при запросе; сохранение другого
   параметра без потери зон; restart; внутри зоны дефект игнорируется, снаружи
   продолжает браковаться; пустые/старые архивные поля корректно отображаются.

## 10. Прямой C++ API для отладки

Frontend должен использовать Java URL выше. Для backend-диагностики доступны:

| Запрос C++ | Назначение |
|---|---|
| `GET /settings/{analysis_profile}?camera_id=0` | Тот же envelope настроек |
| `PUT /settings/{analysis_profile}?camera_id=0` | Тот же частичный JSON с `exclusions` |
| `GET /settings/defaults?camera_id=0` | `settings`/`defaults` с `exclusions=[]` |
| `POST /inspect-shm`, `/inspect-shm-visuals`, `/inspect-test-frame` | Временные зоны в `settings.exclusions` |
| `POST /inspect` (multipart) | Строковое поле `exclusions` с JSON-массивом; `analysis_profile` выбирает профиль |

Прямой C++ inspection-ответ содержит `inspection_exclusions` в корне, а также
`status: "ГОДЕН"|"БРАК"`, `anomaly_score`, `reason`, `settings` и прежние поля.
Полное исключение поверхности даёт `reason="inspection_excluded"`, если шов
не дал другой причины брака. При настройке сохранённых зон ошибка —
`bad_settings`; при некорректном временном override — `bad_request`.

`excluded_normal_zones` и learning API к этим зонам отношения не имеют.
Не вызывайте `/api/camera` из CppDetector: это API отдельного стенда, а не
основного приложения.
