# Постоянный приём аппаратных кадров для наладки — 2026-11-04

Ветка `boobs+pasha`, исходный HEAD `99671642`. Требование владельца:
триггер заведён непосредственно в камеры; приложение постоянно забирает
все готовые кадры. Это не клиентский стрим и не программная съёмка.

## Поведение, подтверждённое исходниками и локальными проверками

В `integration.hardware_frame_reception.enabled=true` запускается отдельный
reader каждой открытой камеры. Он повторяет `capture, wait_frame=true,
preserve_buffer=true`, не ожидая событий DI2/DI3 в Java. Таймаут SDK без кадра
не создаёт инспекцию и сразу возобновляет ожидание. Финальный reader задаёт
`wait_timeout_ms=1000` на запрос: это позволяет выполнять команды настроек
между ожиданиями. Глобальный `frame_timeout_ms=15000` не менялся. Первое
развёртывание с 15-секундным ожиданием показало timeout HTTP настроек камеры
за 3 с; поэтому выбран короткий повторяемый вызов. Физический TriggerSource/
TriggerMode не переключаются этим режимом, `trigger_only`/`start_stream`
не вызываются. Обычная инициализация камер по существующим настройкам сохранена.

Существенное отличие от прежнего `wait_frame`: SDK-буфер **не очищается**
перед чтением. Обычный DI3/legacy window путь по умолчанию сохраняет прежнюю
очистку; `preserve_buffer` задаётся только на конкретную команду.

Кадр копируется из ring-SHM в отдельный pin до следующего чтения.
Имя pin уникально и при сбросе `frame_id` после reconnect. Очередь каждой
камеры FIFO, по умолчанию четыре кадра (`queue_capacity`, 1..64); один reader
не ждёт кадры других камер. При заполнении очереди reader ждёт потребителя
и пишет предупреждение, не выбрасывая уже полученные кадры. После сборки
полного набора перед pipeline есть вторая ограниченная очередь той же ёмкости. Это ограничивает
память; потери камеры/сети/SDK при перегрузке не исключены и не измерены.
Нет обещания бесконечного хранения произвольного входного темпа. Сохраняется
существующий TTL осиротевших SHM-pin 45 с, поэтому длительный backlog не является
надёжным архивом. Сохранение изображений определяется прежними настройками архива.

После уточнения UI полученные кадры объединяются по FIFO: по одному от каждой
из десяти камер получают общий sequence/`inspection_id` и события
`hardware_batch`. Ожидание полного набора происходит
до старта таймаута инспекции. Capture-stage забирает именно этот pin по camera_id
и sequence, не запускает повторную экспозицию/вспышку. При наличии эталона работают
обычные стадии проверки; без эталона — прежний capture-only при
`capture_without_reference=true`. Гейты UI/здоровья по-прежнему управляют инспекцией.
Сам reader от DI-направления, состояния инспекции и наличия эталона не зависит.

В наладке **нет bucket-агрегации и общего вердикта DO3/DO4 по изделию**:
без общего входного DI3 и надёжного идентификатора кадра всех камер нельзя
считать UI-группировку доказательством общего изделия. Результаты идут
обычными сообщениями камер с общим `inspection_id`; фронт собирает по пять
камер своей линии в одну панель истории.
Это диагностический режим, не новая проверенная схема производственной отбраковки.
DI-монитор продолжает обслуживать отдельную подсветку и DI4 shutdown.
Legacy direction window не включается; live-preview не стартует. Клиентский
стрим отклоняется, чтобы не переключать аппаратную камеру в свободную съёмку.

Существующий watchdog не ставит health-RPC за постоянно занятым `wait_frame`:
проверяется живой native client, ошибки/успехи reception RPC сообщают здоровье
через существующий supervisor. При shutdown сначала закрывается приём:
токен отменяет ожидание SDK с опросом 20 мс; затем закрываются камеры и удаляются
неиспользованные pin. Обычный RPC interrupt/reconnect для остановки не требуется.

Assembler ждёт по одному FIFO-кадру всех десяти камер, присваивает набору общий
sequence, затем обычный pipeline использует его как `inspection_id`.

`hardware_batch_sequence`/`hardware_batch_size=10`, источник события —

одной камеры публикация всех десяти ждёт её кадр. Ограничения SDK/TTL выше

прежняя отдельная резервная копия сохранена.
