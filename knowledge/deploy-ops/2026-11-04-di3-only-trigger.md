# Срабатывание съёмки только по DI3 — 2026-11-04

Ветка `boobs+pasha`, исходный HEAD `20909141`, локальные изменения.
По запросу владельца DI2 исключён из условий запуска инспекции.

## Подтверждено исходниками

- В `IoInputDiscreteConfig` режим по умолчанию: `di3_only=true`,
  `require_direction=false`, `require_work=false`, `direction_latch=false`.
- При `di3_only=true` прежние `require_direction`, `direction_latch`,
  `direction_latch_on_work` и `direction_arm_next_di3` отключаются даже при
  значении `true` в старом YAML. Неявное требование DI1 от latch-on-work также
  не включается. Явный `require_work=true` по-прежнему требует DI1.
- Каждый DI3↑ запускает рассылку всем камерам без ожидания DI2. Принимаются
  повторные rising-уведомления без DI3=0 и без переключения DI2.
  Выбор «Прямой/Обратный» в UI не фильтрует съёмку.
- Удалена безусловная проверка DI2 из native hardware frame reception.
  Старый `direction_window_capture=true` в режиме DI3 игнорируется: DI2
  не открывает захват и не отменяет ожидание кадров при спаде.
- Аппаратный путь `In3 → Timer5 → DO5 → Line0` сохранён: Java получает кадры
  через `wait_frame`, программный prefire при аппаратном захвате не вызывается.
- Подписка MVS на DI2 остаётся для отдельной подсветки `interval_flash`:
  сырые DI2-события доходят до слушателей, но обработчик съёмки их игнорирует.
  DI4 и обработка shutdown сохранены.
- Legacy-логика направления доступна только при явном `di3_only=false`
  с соответствующими настройками направления.

Изменены обработчик триггера, defaults, стартовое сообщение и
[`config.exemple/blocks/52-io.yaml`](../../config.exemple/blocks/52-io.yaml).
Локального `config/` в этом checkout нет. Старые ссылки базы на
`52-io-input.yaml` и триггер в `01-core.yaml` не описывают актуальный шаблон:
в текущем агрегаторе импортируется `blocks/52-io.yaml`.
Замеры от окна DI2 за 2026-11-03 сохранены как история прежнего поведения;
их нельзя переносить на новый запуск по DI3.
