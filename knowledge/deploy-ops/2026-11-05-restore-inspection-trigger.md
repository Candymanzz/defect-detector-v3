# Восстановлено поступление кадров после перезапуска — 2026-11-05

Ветка `boobs+pasha`, HEAD `c43e9d4d` плюс локальный диапазон 15 мм.
После [перезапуска 14:13](2026-11-05-restart-metric15.md) пользователь сообщил:
камеры работают, но кадры не поступают на инспекцию. Health компонентов
в предыдущей задаче не был достаточной проверкой рабочего цикла.

## Подтверждённая причина

Рабочий `config/blocks/52-io.yaml` содержал одновременно:

- MVS monitor inputs только In2 и In4, UDP выключен;
- `di3_only: true` и `direction_window_capture: true`;
- `external_hardware_capture: true`, `hardware_line_trigger: true`,
  `immediate_prefire: false`.

До перезапуска прежняя Java исполняла DI2 window path: в журнале
14:11–14:13 последовательности росли до 255, на DI2 было `capture_fired=true`.
Новый загруженный JAR применил DI3-only: `setDirectionWindowCapture()`
явно игнорирует окно DI2, ожидая программное уведомление DI3.
Физические события камер продолжали приходить, но Java не наблюдала
In3: MVS подписан только на In2/In4. В сессии 14:13 реальных фронтов
DI3 не было, `last_sequence=0`, `capture_fired=true` отсутствовал.
Начальная синтетическая выборка DI3=false не является фронтом.

Таким образом, отсутствие захвата предшествовало вызову C++-анализа и
не связано с расширением метрического диапазона. `NO_REFERENCE` был
дополнительным состоянием; при включённом `capture_without_reference`
он сам не должен останавливать поступление кадров.

## Исправление и обоснование

В рабочем YAML изменён только `di3_only: true → false`.
`direction_window_capture: true` оставлен: DI2↑ открывает свежий window
и публикует `wait_frame` всем десяти камерам, DI2↓ закрывает окно.
Существующий аппаратный запуск камеры и отсутствие программного prefire
сохранены. Это восстанавливает фактически работавший путь без изменения
разводки/контроллера, SDK или алгоритма инспекции.

Изменение одного флага выбрано вместо возврата старого JAR: сохраняются
нынешние исправления Java, включая сброс норм при полном запуске и свет.
Добавление мониторинга DI3 потребовало бы отдельной проверки аппаратного
сигнала/длительности импульса; в этой восстановительной задаче оно не делалось.
Git-шаблон DI3-only и исходники Java не менялись: это локальная настройка
существующей установки. При последующем деплое нельзя считать DI3-only
готовым для этой конфигурации без фактического источника DI3 в Java.

Прежний YAML сохранён локально:
`.verification/restore-inspection-20261105/52-io.before.yaml`.
Проверено, что единственное побайтовое изменение — значение этого флага.
SHA256 до: `22de118801959de128c1311bcb05ea8f7b9d671f9da54e26e5d2313bf7173d6c`,
после: `41b41a8424708cb589cea892dde40adc28ffae6b7bde465c809d07f1ec18054c`.
