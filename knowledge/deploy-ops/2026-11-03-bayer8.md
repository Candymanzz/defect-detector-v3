# Bayer8 на десяти камерах — 2026-11-03

Ветка `boobs+pasha`, исходный HEAD `90ef99a7`. Пользователь попросил попробовать
цвет при том же размере передачи, что Mono8. Инвентаризация SDK подтвердила десять
цветных `MV-CS050-10GC`. Камеры автоматически выбрали `BayerRG8`.

## Решение и границы

`camera-worker` разбирает `Bayer8` и четыре явных порядка RG/GR/GB/BG.
Автоматический режим сохраняет текущий Bayer8 либо выбирает вариант из списка
PixelFormat самой камеры. Если его нет, открытие завершается ошибкой: тихого
перехода на RGB8 с тройным трафиком нет. Этот путь реализован для MVS.

Сеть передаёт один байт мозаики на пиксель, как Mono8. SDK
`MV_CC_ConvertPixelTypeEx` восстанавливает BGR8 непосредственно в прежнем SHM-кольце.
Размер SHM остаётся три байта на пиксель, появляется стоимость восстановления
цвета на CPU. Поддержаны плотные строки и padding, проверяются размер входа,
результат преобразования и потерянные пакеты; неполный кадр не публикуется.
Код C++-детектора не изменён: анализ поверхности остаётся по яркости.

При реальном переключении обнаружено, что камера не применяет Gamma в Bayer8.
Гамма теперь задаётся в SDK-конвертере через `MV_CC_SetBayerGammaValue`;
API возвращает это значение, не подменяет его неактивным аппаратным Gamma=1.
Чтение целочисленного BalanceRatio исправлено: SDK-единицы делятся на 1024,
симметрично существующему пути записи. Float-коэффициенты сохраняют единицы.

В рабочих игнорируемых `config/config.json` и `config/blocks/01-core.yaml`
установлен `frame.format: Bayer8`. Шаблон сохраняет Mono8 и описывает переключение.
JNI собрана Release с MVS `/opt/MVS`, опубликована атомарной заменой
`camera-worker/build/libcamera_jni.so`; для её загрузки перезапущен backend.

## Проверки

- С MVS: 4/4 CTest, включая новый `cw_bayer_mvs_tests`. Тест реального SDK на
  синтетических пикселях проверяет четыре мозаики, порядок BGR, обе разновидности
  stride, границы буферов, обрезанный кадр, пакетные потери, гамму и единицы WB.
  Выбор формата проверен с имитацией устройства, включая отказы без fallback.
- Без MVS/Aravis: Release JNI и 2/2 CTest. Java `NativeCameraClientTest`:
  11 тестов, 0 failures/errors/skipped, с JNI без SDK.
- Оборудование: первая проба — по три кадра со всех десяти камер; визуально
  проверен цветной кадр. После исправления гаммы повторены ещё 30 кадров с
  сохранёнными рабочими параметрами: 150 мкс, gamma=0.7, WB red=1.65/blue=1.7.
  Все захваты успешны, формат BayerRG8 → BGR8. Вторая проба дала
  17.69–32.48 мс на одиночный программный захват, включая восстановление цвета.
  Это последовательные software-триггеры, без одновременного аппаратного цикла,
  PLC, производственной вспышки и анализа; не замер полного цикла линии.
- После финального перезапуска HTTP API подтвердил BayerRG8/MVS на 10/10 камер.
  Сравнение с исходными настройками подтвердило прежние размеры и координаты ROI,
  150 мкс, gamma=0.7, WB, gain, black level, таймаут и Line0. Файл
  `camera_runtime_settings.json` побайтово совпадает с резервной копией.
- Java/C++ health доступны. Проксированный API дообучения отвечает 200;
  настройки детектора камеры 0 сохранили 8.6/8.3 мм. Установленный frontend
  совпадает по SHA256 с локальным; `inspect_scale` имеет step=0.01, factor=100 (1%).

Предыдущая библиотека, обе конфигурации, исходные настройки и диагностические
кадры сохранены локально в `.verification/bayer8-20261103-123403/` (не tracked).
Данные эталонов и дообучения не редактировались. Метрические настройки и шаг
масштаба 1% не затронуты исходниками камеры.

Полная серия одновременных аппаратных кадров и сравнение вердиктов с Mono8
не выполнены. Старые эталоны и образцы сохранены, но изменение формирования
яркости после смены формата требует проверки на реальном изделии.

## Переключение обратно

Установить `frame.format: Mono8` в рабочих JSON и YAML и перезапустить backend.
Пересборка не нужна: новая JNI поддерживает оба формата. ROI и сохранённые
настройки камер остаются отдельными от выбора PixelFormat.
