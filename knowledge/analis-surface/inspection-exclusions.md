## Поведение и API: подтверждено кодом

`Settings.exclusions` — массив нормализованных многоугольников `[x,y]` в 0..1.
Максимум 32 зоны, 3–128 точек на зону. Валидируются форма, конечность, границы
и ненулевая площадь. Пустой список отключает исключения. Невалидное сохранение
отклоняет весь patch без частичного обновления других настроек.

Хранение использует существующий `SettingsStore`/`data-dir/settings.json` по
`analysis_profile`. Java proxy `/api/orchestrator/detector-settings/camera/{id}`
уже передаёт GET/PUT без фильтрации новых полей и выбирает настроенный профиль
камеры. Отдельный новый контроллер не нужен. GET defaults выдаёт пустой список;
старые профили без поля совместимы. PUT без `exclusions` сохраняет зоны;
`{"exclusions":[]}` очищает их, DELETE профиля сбрасывает все настройки.

Временный `settings.exclusions` поддержан в JSON-запросах инспекции; multipart
`/inspect` принимает поле `exclusions` с JSON-массивом и `analysis_profile`.
В отличие от старых числовых overrides, неверные новые зоны **не игнорируются**:
выдают HTTP 400/`bad_request`. Это не позволяет молча использовать иной список
при ошибке оператора. Сохранённые неверные зоны дают 400/`bad_settings`.

В основном TEST API черновик передаётся как
`temporarySettings.analysis.settings.exclusions`; настройки не сохраняются.
HTTP 202 означает постановку асинхронного задания, результат приходит через WS.
Прямой контракт C++ и фактическое Java-проксирование проверены тестами; полный
путь нового редактора в браузере остаётся задачей фронтенда.

## Алгоритм и согласованность

Механика Reference/inspectFrame/seam перенесена из проверенной реализации
CppDetector; базовые файлы перед переносом совпадали с standalone baseline.
Зоны вычитаются из ROI до статистики яркости, diff, learning, компонент/score.
Знаменатель score — оставшаяся площадь. Маски верхних углов строятся до вычитания
дыр; исключённые пиксели обнуляются и в них. Hann-окно позиционирования маскируется.
Ореол heatmap тоже обрезается внутри зон. Пустой список сохраняет прежний путь
без дополнительного построения маски.

Полностью исключённая поверхность возвращает score 0, `surfaceSkipped=true`
и `reason=inspection_excluded`, даже при sensitivity=1. Шов продолжает отдельно
работать вне зон. Пересекающие исключение сечения не участвуют в fit/coverage;
многоугольники переносятся в сырой кадр на компенсированный сдвиг поверхности.
Если вне зон найден брак шва после пропуска всей поверхности, причина становится
`seam_deviation`, а `surfaceSkipped` остаётся true. Отдельная Java-геометрия,
проверка обязательных камер и отправка PLC не менялись.

Основное приложение имеет параллельные инспекции и временные overrides, поэтому
исключения **не устанавливаются изменяемым полем общего Reference**. Метод
`prepared(scale, exclusions)` возвращает неизменяемый Prepared с конкретным
списком зон. На масштаб хранится один последний вариант; другая параллельная
инспекция сохраняет свой shared_ptr, даже если cache уже сменился. Это исключает
взаимное влияние запросов без безграничного кэша всех вариантов черновика.

## Java, WebSocket и архив

C++ inspection-ответ и inspection-log содержат отдельный объект:

```json
{
  "inspection_exclusions": {
    "polygons": [],
    "coordinate_space": "normalized",
    "surface_skipped": false,
    "remaining_area_work_px": 12345.0
  }
}
```

Это поля фактической инспекции. `CppAnalisSurfaceHttpSupervisor` переносит объект
в RPC response; `InspectionExclusionDiagnostics` рекурсивно копирует вложенные
списки/карты. `InspectionDecision.inspectionExclusions` принадлежит своему кадру.
Сохранены конструкторы старых производителей решения. Старые/Python ответы
дают пустую карту; learning и `excluded_normal_zones` не переиспользуются.

`WsOutboundMessenger` публикует объект в `server.inspect_result.payload`.
`FrameArchiveService` сохраняет его в корне result.json и читает после restart;
history endpoint выдаёт его в каждом frames[]. Существующие архивы без поля
читаются. `UiArtifactsSidecar.applyOriginalHeatmapSettings` копирует также исходные
`exclusions` в settings отложенного запроса карты: последующее изменение профиля
не должно менять визуализацию прежнего кадра. Старый response без поля задаёт
пустой исходный список для такого повторного расчёта.

## Отличия от standalone и принятые решения

Выбрано хранение в существующем профиле камеры: оно уже постоянное и доступно
через Java API. Standalone хранит пиксели в своём config и сбрасывает их при смене
размера эталона; основной сервис использует нормализованные точки, поэтому зоны
сохраняются с профилем при перезагрузке/смене эталона и размера. Они не ограничены
fingerprint нормы. Это нужно явно учитывать в редакторе нового эталона.

Оставлен отдельный список дыр в ROI: сокрытие overlay не меняет вердикт, а
фильтрация целого bbox аномалии могла бы скрыть дефекты за контуром исключения.
Вторую БД или product-scoped API вместо существующих профилей не добавляли.
Отдельный immutable cache нужен из-за конкурентных временных overrides;
одна изменяемая маска общего эталона была бы некорректна.

Компромиссы: зоны безусловно скрывают дефекты внутри; слишком тесная граница
оставляет влияние размытия за её пределами. Шов исключает целое сечение своей
полосы поиска. API заменяет массив целиком, без revision/ETag; сохранения редактора
следует сериализовать. Нормализация сохраняет относительное положение зон при
изменении разрешения, но не подтверждает правильность зон для нового изделия.

## Проверки

Подтверждены локально на Windows, MSVC 19.44/OpenCV 4.14 и JDK 17:

- Изолированная Release-сборка основного C++; **9/9 CTest**. Новый exclusion_test
  покрывает валидацию/атомарность, профиль/restart/clear, дефект внутри/снаружи
  при масштабах 1/.73/.5, перенесённый кадр, маски/знаменатель/corners/heatmap,
  перекрытия, полное исключение и seam вне полностью исключённой ROI.
- Четыре параллельных потока по 12 инспекций одного Reference с разными масками:
  исключения не перетекают между запросами.
- Новый `exclusion_http_test.cjs`: defaults, сохранение до загрузки эталона,
  JSON/multipart overrides, изоляция профиля, errors, сохранность настройки при
  невалидном PUT/обновлении другого поля, raw heatmap, restart и reset.
  Прежний `robust_learning_http_test.cjs` также прошёл.
- Полная компиляция **290 main + 113 test** Java-файлов; **28/28 профильных JUnit**:
  новый proxy/settings test, HTTP decode → frame decision, immutable nested maps,
  archive restart/history API, queued WS, original-mask heatmap replay и прежние
  learning/archive/aggregation/deferred-transport проверки.
- UI исходники не изменены; frontend-сборка не нужна для изменённых серверных
  файлов и не выполнялась. Ненужные зависимости не добавлялись.

При HTTP-проверке raw maps потребовалось выделить файлы в штатном SHM-каталоге;
на Windows `writeU8Image` проверяет пути до записи. Fixture создаёт отдельный
временный `LOCALAPPDATA/iml_shm` и файлы вывода; контракт приложения не ослаблялся.
Java sandbox запретил чтение JUnit JAR из Maven-кэша; после разрешения тот же
javac/JUnit прошёл. Это не проверка Maven shaded JAR.

Артефакты: `.verification/main-exclusions/build/Release/`, результаты JUnit —
`.verification/main-exclusions/java-tests.log`. Локальная `.verification` игнорируется.
Рабочие данные/сервисы не перезапускались и не переписывались; commit/push не было.
Для применения к runtime нужны обычная сборка/установка C++ и Java, затем restart.

Не проверены Linux, MVS/камеры/PLC, полный цикл 500 мс, размеченное качество и
интерактивный браузер. Прежняя standalone parity на 800 кадрах относится к тому
стенду; новый основной перенос не объявляется повтором этого прогона.
