## Сохранение настроек

Использовано ранее проверенное решение SettingsStore из `compensation / 79483801`.
`set` и `reset` готовят следующую карту профилей отдельно. Рабочие значения и
выходной Settings меняются только после успешной записи файла. Если создание,
запись, flush, закрытие или замена файла не удались, выбрасывается ошибка
с операцией и путём; старые настройки остаются действующими.

JSON полностью записывается в эксклюзивный временный файл в том же каталоге,
затем заменяет основной. Уникальное имя включает PID/время/счётчик. Прямой
fallback с обнулением основного JSON удалён. Неудачная операция очищает свой
временный файл. Windows использует WriteFile/FlushFileBuffers и MoveFileExW
с replace/write-through; POSIX — write/fsync/close/rename. Для коротких
Windows sharing/access conflicts есть до пяти попыток с суммарным ожиданием
не более 75 мс. Межпроцессная сериализация обновлений не добавлена.

PUT уже обрабатывал исключения через общий HTTP guarded-handler. DELETE
переведён на него тоже: ошибка сброса возвращает **HTTP 400, io_error**, а
успешный ответ и сообщение `settings saved/reset` при отказе не выдаются.
Frontend и Java proxy не менялись; действующий контракт ошибок сохранён.

## Повторное использование кэша

`inspectFrame` передаёт в `compareLearned` **тот же const Prepared&**, который
подготовлен для текущего масштаба, ROI и исключений. Matcher читает из него
upperCornerArea и refGray, не вызывает `Reference::prepared(scale)` без зон.
Это убирает два запроса, которые подменяли кэш вариантом без исключений и
заставляли следующий кадр готовить его снова.

Время жизни обеспечивается shared_ptr текущей инспекции; изображения не
копируются. Реальное изменение ROI/масштаба/зон по-прежнему может перестроить
подготовку. Одновременные запросы с разными наборами зон могут заменить
последний вариант кэша, не изменяя снимок уже работающей инспекции.

В этой ветке используется refGray. Перенос адаптирован к этому API; отдельная
обработка ROI-границ из compensation в эту задачу не включена. Формула score,
ослабление сравнения, миллиметры и позиционирование не переписывались.
Два прямых вызова matcher в placement-тесте обновлены под параметр Prepared.

Передача готового снимка выбрана вместо повторного lookup с exclusions:
она исключает ненужное обращение к кэшу и сохраняет именно подготовку
текущего запроса при параллельных вариантах зон. Полное слияние compensation
не выполнялось, чтобы ограничить изменение двумя выбранными ошибками.

  **13/13 CTest** прошли, включая новый settings_store_test и обновлённый exclusion_test.
- settings_store_test: **70 проверок** — создание/восстановление профилей,

  создания каталога и Windows-блокировка замены, неизменность памяти/файла/
  выходного параметра при отказе, reset, очистка своего временного файла,
  чтение целого JSON другим потоком во время 30 сохранений.
- exclusion_test дополнен **88 инспекциями**: три варианта зон, четыре
  масштаба 21/50/73/100%, чувствительность 50/80%, повторные и параллельные
  вызовы с нормой. Объекты Prepared/alignment сохраняются между одинаковыми
  запросами; кэшированная картинка не меняется, self-comparison остаётся score=0.
- **Оба новых теста отдельно связаны со старым ядром 9b080256.** Старый
  SettingsStore: exit=1, `failed persistence must not return success`;
  старый matcher: exit=1, `learned comparison replaced the inspection's prepared/cache variant`.
  Это отрицательные контроли исходных ошибок, не неудачная сборка.
- Настоящий HTTP-сервис: **17 проверок, 15 запросов, три запуска** одного
  изолированного состояния. Заблокированные PUT/DELETE возвращают ошибку,
  старые значения/байты сохраняются. После разблокировки запись работает;
  новый порог, мм и масштаб переживают рестарт, reset тоже переживает рестарт,
  другой профиль камеры не теряется.
- HTTP learning с постоянными зонами прошёл: обученная движущаяся тень
  принимается, новая царапина отклоняется; временные overrides не сохраняются;
  настройки и зоны восстанавливаются при рестарте C++ тестового процесса,
  удаление нормы возвращает брак на обученной тени.

Тестовые процессы запущены скрыто на localhost со своим data/log/LOCALAPPDATA;
остановлены только процессы этих тестов. Сохранение норм при рестарте одного
C++ процесса соответствует recovery текущего запуска Java; правило очистки
при полном старте приложения не менялось.
