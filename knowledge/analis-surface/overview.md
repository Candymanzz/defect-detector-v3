# Текущий детектор: C++ и допуски смещения в мм

**Код: `ppc-reserv`, перенос из `CppDetector/123` (`244cea1`), 2026-10-28.** Основной backend — **`cppAnalisSurface`**. [Полный состав переноса](../../cppAnalisSurface/INSPECTION_PORT.md). Замеры от 2026-10-27 ниже исторические.

## Алгоритм

Вход основного `/inspect-shm` — BGR8-кадр и эталон соответствующей камеры/изделия. Внутри `inspectFrame` оба изображения переводятся в **grayscale**, масштабируются и размываются Gaussian 5×5. Текущий surface score рассчитывается по яркостным различиям, без отдельного сравнения цветовых каналов. Формат захвата камеры Bayer8/Mono8/BGR8 и формат сравнения — разные этапы.

`Reference::prepared(scale)` кэширует подготовку эталона: серое изображение, ROI-маску, область обработки, миниатюру и Hann-окно. Ключ масштаба округляется до тысячных; смена ROI очищает подготовленный кэш.

Далее выполняются:

1. Оценка переноса `phaseCorrelate` на миниатюре ROI с максимальной стороной 256 px.
2. Компенсация переноса через `warpAffine`, без вращения, scale fitting и перспективы.
3. Нормализация яркости текущего ROI по среднему/СКО эталона.
4. Сравнение с локальным min/max-конвертом эталона, допускающим различия положения по X/Y.
5. Пиксельный порог чувствительности, морфологическое открытие 3×3, связные компоненты, отсев по числу пикселей и подсчёт отмеченной площади без чистых отверстий.
6. Score и вердикт. Если включена отдельная проверка линии шва, она также может забраковать кадр.

Нормы, FP-зоны, векторный поиск, нейросетевое дообучение и Python-перепроверка в этот путь не входят. Часть совместимых Java-команд для FP является no-op с `supported:false`.

## Настройки

Значения API — реальные числа ниже; UI переводит доли в проценты.

| Поле | Диапазон / default | Фактический смысл |
|---|---|---|
| `sensitivity` | 0…1 / 0.5 | Пиксельный порог `cvRound(80 - 75*sensitivity)`: выше чувствительность → легче отметить отличие. |
| `threshold` | (0…1] / 0.6 | БРАК при `anomaly_score >= threshold`. Меньше порог → строже. |
| `horizontal_shift_tolerance_mm` | 0…10 мм / зависит от камеры | Допуск локального сравнения и предел общего смещения по горизонтали. |
| `vertical_shift_tolerance_mm` | 0…10 мм / зависит от камеры | Аналогичный вертикальный допуск. |
| `shift_tolerance_x` | дробные 0…30 / 3 | Legacy-допуск в пикселях исходного кадра; в сохранённых профилях преобразуется в начальные мм. |
| `shift_tolerance_y` | дробные 0…30 / 3 | Аналогичный вертикальный legacy-допуск. |
| `min_blob_area` | 1…100000 / 20 | Минимальная площадь связной компоненты в исходных px²; на рабочем масштабе умножается на `scale²`. UI имеет более узкий диапазон. |
| `inspect_scale` | 0.1…1 / 1 | 1 = исходное разрешение; 0.5 = половина каждой стороны, четверть числа пикселей. |

**Ноль чувствительности в текущем C++ не означает «всегда ГОДЕН».** Порог отличия становится 80; сильное отличие, `shift_exceeded` или включённый seam всё ещё могут дать БРАК. Прежний договор о полном отключении при нуле относится к старому Python-поведению и требует отдельного решения для C++.

### Миллиметры

Масштабы камер временно взяты из 123 для базового изображения 1224×1024. При изменении цифрового разрешения
мм/пиксель пересчитываются по соответствующей оси. Дробные пиксели сохраняются до построения рабочего конверта;
предел общего смещения соответствует заданному числу мм независимо от Downscale. Точность измерения зависит
от разрешения анализа и калибровки. UI не требует отдельного шага калибровки, а явно отмечает приблизительность мм.

Оркестратор передаёт camera_id отдельно от analysis_profile. Настройки `/settings/:profile?camera_id=N`
возвращают масштаб соответствующей камеры; старые файлы профилей продолжают читаться и получают начальные мм.
Новые поля диагностики: shift_mm, shift_raw_mm, shift_limit_mm, mm_per_pixel, metric_scale_source,
effective_shift_tolerance_mm и analysis_pixel_mm. См. таблицу и примеры в INSPECTION_PORT.md.

### Совместимость прямых X/Y-запросов в px

Для `s = inspect_scale`:

```text
tolWorkX = max(0, lround(shift_tolerance_x * s))
tolWorkY = max(0, lround(shift_tolerance_y * s))
kernel = (2*tolWorkX+1, 2*tolWorkY+1)
maxShiftX_original = max(8, 4*tolWorkX) / s
maxShiftY_original = max(8, 4*tolWorkY) / s
```

Эти формулы относятся к прямому legacy px-override без соответствующей мм-оси. Обычный путь сервиса и UI
использует мм; сохранённые legacy профили получают начальные мм с базового разрешения.

Это две осевые настройки. При X=Y=3 и масштабе 100% конверт сравнения 7×7, предел надёжной компенсации ±12 исходных px по каждой оси. Поэтому перенос 6 px может быть исправлен при настройке 3 px.

При X=0 по X отключается ширина конверта, но остаётся минимальный предел компенсации 8 рабочих px. Уменьшение масштаба меняет этот предел в исходных пикселях. Ноль оси не является общим выключателем positioner.

Оценке с `response < 0.05` не доверяют, перенос зануляется. Если оценённый перенос больше лимита, компенсация не применяется; при `response >= 0.3` также ставится `shift_exceeded`. Значит, **брак по чрезмерному сдвигу всё ещё возможен**. Не обещать полное исчезновение любой отбраковки, связанной с положением.

Старое поле `shift_tolerance` принимается как значение обеих осей; явные `shift_tolerance_x/y` имеют приоритет. Оно служит совместимости, а не третьим независимым регулятором. Настройки профиля сохраняются через `/settings/:profile`; временные overrides отдельного запроса не сохраняются. Неверные сохранённые настройки отвергаются, неверные отдельные overrides могут игнорироваться.

### Шкала score

```text
area_percent = 100 * flagged_pixels / roi_area
anomaly_score = min(1, area_percent / 0.2)
```

При пороге 0.6 отбраковка по score начинается примерно от **0.12% отмеченной площади ROI**, после фильтрации компонент. Это не вероятность дефекта. Другие причины отказа проверяются отдельно. Подсказка UI согласована с этой шкалой; шкала `/5*3` из 123 не перенесена по решению владельца.

С 2026-10-28 миниатюры и Hann-окно дополняются нулями до одинакового чётного оптимального DFT-размера.
Это устраняет ложный сдвиг 0.5 пикселя при нечётном размере DFT. Координатный масштаб берётся до padding;
рабочий clone перед correlation сохранён. При включённой проверке стыка ненайденная линия отклоняет кадр
с reason=seam_not_found, если нет более ранней причины брака. min_contrast передаётся в измерение краёв стыка.

## Исправление кэша

До `bfd9b54a` `phaseCorrelate` получал напрямую `prep->refSmall`. В OpenCV на пути без DFT-padding применение Hann-окна могло изменять общий буфер. Файл эталона при этом не менялся, но повторные инспекции портили кэшированную миниатюру и теряли компенсацию.

Исправление — `prep->refSmall.clone()` как рабочий буфер каждого вызова. Числа порогов, ROI и логика X/Y при этом не менялись.

Локально: camera_2, квадратный ROI, тот же кадр со сдвигом +6 px: **41/60 ложных отказов до → 0/60 после**. На 20 сочетаниях камера/ROI кэш остался неизменным. На 1000 кадрах результаты первого вызова совпали с прежним алгоритмом; проверены повторы, общий кэш и параллельный холодный старт. Непрерывный тест скорости также не выявил изменения результата одинакового кадра.
