# Надёжное сохранение и сброс настроек C++ — 2026-11-09

Репозиторий `detector-/defect-detector-v3`, ветка `compensation`, исходный HEAD
`637a57f44e9dfb3534c4d7cf8327817e7eab2bd0`. Пользователь разрешил исправить
выдачу успешного сохранения при ошибке записи. Предыдущие незакоммиченные
заметки аудита сохранены. Изменены SettingsStore, HTTP reset-handler, CMake
и новый регрессионный тест; рабочие конфиги и установленные процессы не менялись.

## Поведение

- `set` и `reset` сначала формируют копию карты профилей. Живая карта и выходной
  параметр `set` обновляются только после успешной записи файла. При отказе
  изменения не остаются только в памяти.
- JSON записывается в отдельный временный файл **в том же каталоге**. Его имя
  включает процесс, монотонное время и счётчик; создание эксклюзивное, поэтому
  чужой/оставшийся временный файл не перезаписывается.
- Проверены создание каталога/файла, полная запись, flush и закрытие. Windows:
  CreateFileW/WriteFile/FlushFileBuffers/CloseHandle, затем MoveFileExW с
  REPLACE_EXISTING и WRITE_THROUGH. POSIX: open/write/fsync/close и rename.
- Прямой fallback с обнулением основного JSON удалён. При неудаче временный
  файл, созданный этим вызовом, удаляется; старый файл сохраняется.
- Windows может временно отклонять rename при открытии файла читателем или
  сканером. Только sharing/access conflicts повторяются максимум пять раз,
  с общей задержкой до 75 мс. Устойчивая блокировка возвращает ошибку.
- После фиксации карта меняется через swap; ближайшее чтение повторно сверяет
  файл, чтобы не записывать в кэш timestamp чужого одновременного обновления.
- PUT уже использовал общий guarded-handler. DELETE теперь использует его
  тоже: сбой сброса возвращает JSON `error_code=io_error`, HTTP 400 по текущему
  контракту сервиса. Сообщение содержит операцию и путь к settings-файлу;
  ответ об успехе и запись лога «settings saved/reset» не выполняются при отказе.

Frontend уже отклоняет HTTP-ошибки в HttpClient, извлекает `detail` через
errorMessage и ставит error-status в DetectorSettingsPanel. Java proxy
передаёт HTTP-ответ. Эти участки проверены чтением кода, без изменений;
браузерный сценарий в этой задаче не запускался.

## Почему выбран такой подход

Проверки одного ofstream недостаточно для согласованного состояния: старая
реализация сначала изменяла map, а при неудачном rename перезаписывала основной
файл напрямую. Выбрана фиксация полностью подготовленного файла перед swap
карты. Нативный flush делает ошибку сброса данных наблюдаемой до замены.

Для Windows использован
[MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)
с заменой существующего файла. Широкий fallback на прямую запись не применяется.
ReplaceFileW без отдельной схемы восстановления не выбран: его документация
описывает также частичные состояния при некоторых ошибках замены.
[Документация ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

## Проверки

**Новый settings_store_test: 70 проверок на Windows Release.**

- Родитель settings.json — обычный файл: операция выбрасывает I/O-ошибку,
  нового профиля в памяти нет, выходной Settings не изменён, блокирующий файл цел.
- Первое сохранение создаёт вложенный каталог, в том числе с кириллицей.
  Сохраняются чувствительность, порог, масштаб, допуски в мм и флаг обучения;
  новый SettingsStore восстанавливает значения. Другой профиль сохраняется.
- Невалидное значение не пишет файл, сброс отсутствующего профиля не пишет его,
  успешный сброс удаляет только нужный профиль и переживает перезапуск.
- Неявные приблизительные масштабы не становятся явно откалиброванными после
  сохранения. Чужой `.tmp` не повреждён.
- Открытый Windows-handle запрещает замену целевого файла. Неудачные изменение,
  создание нового профиля и reset не меняют файл/живую карту, временные файлы
  очищаются; новый экземпляр хранилища читает прежние значения.
- Другой поток непрерывно читает JSON с sharing-delete во время 30 сохранений:
  не увидел отсутствующего/частичного JSON. Первый вариант без повтора rename
  обнаружил временный Access denied; добавлен ограниченный повтор и проверка прошла.

Тот же новый тест отдельно собран со **старым** production SettingsStore:
exit=1, `failed persistence must not return success`. Это подтверждает,
что регрессия воспроизводит исходную проблему.

**Настоящий HTTP-сервис: 17 проверок, 15 запросов, три запуска одного состояния.**

1. Два профиля камер сохранены через PUT.
2. settings.json заблокирован отдельным Windows-handle: PUT и DELETE получают
   HTTP 400/io_error с detail; GET возвращает прежний порог, байты файла прежние.
3. После снятия блокировки PUT успешно сохраняет новый порог.
4. После действительного перезапуска C++-процесса восстановлены порог, оба
   допуска в мм и масштаб; второй профиль сохранён.
5. После DELETE и ещё одного перезапуска удалённый профиль имеет default,
   его нет в JSON; второй профиль по-прежнему сохранён.

Тестовые серверы запускались скрыто на localhost/случайных портах с отдельными
data/log/LOCALAPPDATA в артефактах; остановлены только созданные тестовые процессы.

## Ограничения

- Проверено на Windows/MSVC/OpenCV4.14. POSIX-путь реализован, но Linux-сборка
  и исполнение в этой задаче не выполнялись.
- Реальное заполнение диска и аппаратное отключение питания не имитировались.
  Сохранение проверяет системные ошибки write/flush/close/rename; гарантии
  против аппаратных сбоев накопителя и для всех файловых систем не заявляются.
- Замена файла целиком не сериализует одновременные изменения разных процессов:
  внешний процесс может записать более позднюю версию. Межпроцессный lock и
  транзакция сразу нескольких camera-profile в эту задачу не входят. Один
  SettingsStore по-прежнему сериализует свои операции mutex.
- Автоматической смены каталога при отсутствии прав нет: пользователь получает
  ошибку с путём, прежние значения остаются действующими.
- Другие семь пунктов аудита, правила инспекции, пересчёт мм и поведение
  чувствительности 0% этой задачей не изменены. Runtime не обновлялся.
