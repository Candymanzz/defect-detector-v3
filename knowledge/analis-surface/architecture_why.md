## 1. State model: RAM references, per-request ROI, disk for settings/learning
- References live **only in RAM** (`InspectionService.references`) **[doc]** `analisSurface/docs/GUIDE.md` (“эталоны … хранятся в памяти процесса и теряются при перезапуске”). Because six uvicorn processes each have their own RAM, the orchestrator replays `set_reference_shm` to every unique server and tracks a signature per `(product, camera)` (`SHARED_REFERENCE_SIGNATURES`), re-uploading whenever descriptors or file content fingerprint change (reference retake with the same shm name must bust caches: `reference_content_fingerprint`).
- ROI and perspective line travel in **every** inspect request **[doc]** `schemas.py` comment: “Carry the camera-scoped ROI with each request so a Python restart cannot silently fall back to full-frame processing.” Missing perspective line is *also* applied (`set_perspective_line(None)`), so stale lines from a previous product never leak.
- Persistent disk state (analysis settings, FP zones + crops, sub-zones, accepted normals, reviews) uses file signatures / generation tokens so the six processes converge (`_reload_analysis_settings_if_stale`, `fp_zones.generation`, `_publish_storage_generation`) — ⚠️ [GUESS/CONJECTURE] added after the move from one process to six (`0da1c38e`, 2026‑10‑15), since operator edits via one process had to be visible to the others.
- Camera-scoped products (`product#cam=N`, created in Java) isolate references/ROI/FP-zones per camera while *analysis settings* are per `analysis_profile` (per camera as well, `bench-lanN`) — settings can still be shared by profiles if wanted.

## 2. Processes × threads and priorities
- The checked-in launcher template uses 6 processes × 3 inspection threads (`analis_surface.inspect_workers` → `ANALIS_INSPECT_WORKERS`); Python defaults to **10** threads if the environment variable is absent (clamped 1–32). Process count and threads are configuration, not a universal runtime fact. OpenCV is pinned to 1 internal thread: **[code]** `dependencies.py` prevents nested OpenCV teams from oversubscribing the CPU when ten cameras arrive together.
- `InspectionWorkload`: auxiliary CPU/disk work (history, deferred heat-map) must never delay a verdict. Foreground counter is incremented **when a request is queued**, not when it starts (`InspectionExecutor.submit`), so background tasks also yield to requests still waiting for a worker. Background work has a deadline (3 s) and a bounded queue (4) → drop (`429`) rather than accumulate **[code]**.
- Deferred heat-map (`defer_heatmap`) and deferred review (`defer_learning_review`): verdict first, artifacts later — `INSPECTION_OPTIMIZATION.md` (“Render the original result after PLC delivery, without repeating inspection”).

## 3. Why classical CV (and why ML was removed)
- The pipeline is a calibrated *difference-to-reference* detector with explicit, explainable stages (positioning → light compensation → shift-tolerant envelope → morphology → shape scoring) and operator-tunable parameters. Verdicts must be deterministic and explainable to line staff; the learning mechanism is *memory of approved false positives* instead of retraining **[doc]** `LEARNED_NORMALS.md`.
- Commit `db7e2961` (2026‑10‑16 “удалил все с моделями и anomalib”) **[code, from the diff]**: removed `anomalib` from `requirements.txt`; removed `self._anomaly_engine = None; self._load_anomalib_engine()` (loaded `OpenVINOInferencer(path="models/patchcore/openvino/model.xml")`, silently `None` on any exception) and the branch in `_run_anomaly_model` that, when `settings.use_patchcore` and the engine existed, returned `max(model_score, heuristic_score)` with `mask = model_mask | heuristic_mask`. So the ML branch was *optional and already silently inactive when the model file was absent*. ⚠️ [GUESS/CONJECTURE] production ran without the model (no weights exist in git — the commit touches only the two files above — and the heuristic is the sole verdict path) — the cleanup removes a dependency and a dead path. `AnalysisSettings.use_patchcore` (and `_COARSE/_SENSITIVE/_FIXED_FIELDS`) and `docs/GUIDE.md` still mention it (stale, harmless: the flag is no longer read).

## 5. FP zones and learned normals — two different false-positive mechanisms
- **FP zone**: a region drawn by the engineer (UI FP editor) that always produces a false defect; stored as polygon + a **mini-etalon crop** of the false picture. It is punched out of the main score; if it "triggers" vs the main reference the crop of the current frame is compared with the stored mini‑etalon — only a match is excluded, so a *real* new defect inside the zone is still caught (commits `d5935541`, `45a008c6`, `0042e6bb`, 2026‑07‑24).
- **Learned normal**: post-factum labelling by operator of one specific defect from a past inspection (`7d39b0db`, 2026‑08‑13; history stores PASS **and** REJECT: `972efdc0`). Matching uses position (px tolerance) + shape similarity and only suppresses the matched component (“A saved broad normal may still contain a new scratch”). Works after alignment, in the analysis frame's pixel space (comment :40-45), not in percentages of the frame.
- Order in the pipeline: learned normals ➜ FP recheck ➜ regional scoring, so each stage sees the result of the previous one **[code]**.
- **[code, reviewed 2026-10-20]** `AcceptedNormalMemory.apply` refreshes the generation under its lock. A changed generation invokes `_load`, which clears/reloads the whole JSON/NPZ store, including saved images, before filtering cases for the current product/reference. Cross-process consistency exists, but refresh work can run synchronously during inspection.
- **[logs: 2026-10-16]** the combined learned-normal/FP interval reached 1019.541 ms during learning updates; the existing timer does not isolate the reload cost from matching/rechecking. Treat finer profiling, prepared snapshots and selective C++ as [proposals](./optimization_plan.md), not implemented fixes or proven speedups. See the [dated evidence](../performance/2026-10-16-log-review.md).

## 6. Settings model
- Two-level UI model (`165b880b`, 2026‑08‑11 “базовые и расширенные настройки по паролю”): *Simple* (`threshold`, `sensitivity`) for operators and *Detailed/Pro* six group strengths for engineers; both map to the 25-field `AnalysisSettings` through `expand_merged` so the algorithm only sees concrete numbers. Strength semantic: 50 = group follows sensitivity as stock; 0 = group stays at stock; 100 = twice as strongly (`effective_group_sensitivity`).
- Settings are *effective-value overrides* + remembered knobs, so the UI can show the knob positions after a restart.
- YAML anchors `setting_ranges`/`knob_ranges` were built for per-installation retuning (`4ee2291c`) but are **currently dead** (see [overview §5](./overview.md#analysis-settings)).

## 7. Removal/keeping decisions worth remembering
- Heat-map for the UI is gray‑u8 only; colourisation happens in the front-end worker (payload small). Colour heat-map code (`_colorize_heatmap`, `_colorize_heatmap_29c9cfa`) remains for the legacy multipart endpoints and pre-learning heat-map reproduction (`29c9cfa` is the pre-learning commit referenced in comments).
- `/inspect`, `/upload-ref`, HTML test pages are retained for bench work without cameras.
