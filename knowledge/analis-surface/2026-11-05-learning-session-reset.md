# Дообученные нормы на один запуск приложения — 2026-11-05

`detector-/defect-detector-v3`, `boobs+pasha`, исходный HEAD `37499f9e`.
После обсуждения коллизии frame_id пользователь уточнил требование:
**нормы сбрасываются при полном перезапуске приложения**. В отдельном
ответе выбрана именно эта граница, а не автоматический рестарт C++ и
не «Стоп → Пуск» инспекции.

## Итоговое поведение

| Событие | Что происходит с дообученными нормами |
|---|---|
| Полный запуск Java-приложения | Удаляются со всех C++-серверов пула до продолжения запуска |
| «Стоп → Пуск», очистка/повторная отправка основного эталона | Текущие нормы сохраняются по прежним правилам привязки к эталону |
| Восстановление HTTP-клиента или отдельный рестарт C++-процесса | Нормы текущего запуска восстанавливаются из прежнего хранилища |
| Переподключение WebSocket или перезагрузка браузера | Список локальных миниатюр сверяется с сервером; действующие нормы сохраняются |

Сброс касается learned-regions, а не основных эталонов, ROI или параметров
анализа. Формула score и алгоритм сопоставления не менялись. При следующем
полном запуске после установки изменения существующие нормы будут удалены;
это запрошенный пользователем жизненный цикл.

## Реализация

`ChildProcessStartupService.start` после создания непустого C++ HTTP-пула
вызывает сброс для каждого уникального `baseUrl` ровно один раз. Это
находится в bootstrap приложения, не в `CppAnalisSurfaceHttpSupervisor.start`,
`restart`, инспекции или WS stop/start. Разные URL очищаются независимо;
несколько HTTP-клиентов одного сервера не вызывают повторных удалений.

Новый метод клиента `resetLearnedNormalsForApplicationStart` использует
существующий `DELETE /learning/accepted-cases`, проверяет корректный
булевый `deleted` и затем подтверждает пустой `cases` через GET. Успешное
удаление при уже пустом списке (`deleted=false`) допустимо. Ошибка HTTP,
пустой/некорректный ответ или оставшиеся cases останавливают bootstrap,
чтобы приложение не продолжило работу со старыми нормами. Это не меняет
прежний permissive decoder обычных inspection responses — его отдельный
баг здесь не исправлялся.

C++-реализация удаления уже очищает метаданные, активные Reference learned
списки и файлы crop. Её существующая персистентность сохранена для
автоматического восстановления C++ в рамках той же Java-сессии.

В интерфейсе `server.hello` запускает сверку сохранённых case IDs с
`GET /api/client/learning/accepted-cases` без фильтра по камере. Сверка
дожидается восстановления IndexedDB, одним изменением удаляет отсутствующие
нормы из архивных копий/миниатюр и записывает обновлённую библиотеку обратно.
Основные картинки/контуры сохраняются. Новые IDs, добавленные во время
GET, не удаляются по устаревшему снимку. При недоступном API или неверном
формате локальные копии сохраняются; сверка повторяется при следующем
подключении. Она сама не удаляет действующие нормы на детекторе.

## Границы исправления

Сценарий коллизии между полными запусками из аудита теперь предотвращается
самим сбросом старых норм. Дедупликация C++ внутри одного запуска по
source_inspection_id не менялась: отдельный перезапуск только камеры/worker
при продолжающейся Java-сессии может повторить frame_id и остаётся отдельным
случаем. Это не основание очищать нормы при обычном Stop/Start вопреки
выбранному пользователем требованию.

Другие пункты аудита — UNKNOWN→ACCEPT, потеря capture-цикла, ненайденный
стык, гонка ROI, запись настроек, вырожденный ROI, общий reference cache
разных backend и ECC/яркость — этой задачей не изменены. Работа на Linux,
реальных камерах/PLC и полный запуск станка с новым bootstrap не проверены.
Для применения нужна пересборка Java и frontend; C++ API уже поддерживает
необходимый DELETE/GET, его алгоритм менять не требуется.
