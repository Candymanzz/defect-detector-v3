# 2026-11-17 — Пакет из десяти кадров comp+: время и точная оптимизация

## Задача и исходное состояние

Пользователь попросил измерить полный проход десяти кадров в comp+ и
проверить оптимизацию при превышении 500 мс. Исходники на `5f8ca896`,
предыдущие незакоммиченные заметки сравнения веток сохранены.

Сервис уже обрабатывает запросы параллельно, OpenCV внутри одного запроса
работает одним потоком. В локальном `config/config.yaml` один процесс,
`python_parallelism: 10`, `python_request_parallelism: 10`,
`analis_surface_autostart.inspect_workers: 3`. Linux-команда дополнительно
закрепляет три слота за CPU `3-5`; автоматически менять число слотов
без согласования CPU-списка и топологии нельзя. Конфиг не изменялся.

Измерена задержка от запуска всех десяти запросов до получения всех десяти
результатов, а не сумма времен параллельных запросов. Данные BGR читаются
через настоящий `Service::inspectShm`: очередь слотов, чтение SHM-файла,
настройки/эталон, предобработка, позиционирование, маска, аномалия, штатный
вызов проверки шва. Шов не настроен; дообученных норм в тестовых профилях
нет. HTTP дополнительно измерен отдельным прогоном.

Аппаратный захват, Java-оркестрация, PLC, создание и запись хитмапов,
обученные пользователем нормы, холодный диск и фактическое Linux-affinity
в эту оценку не входят. Это полный проверяемый проход локальной инспекции
из подготовленных кадров, не обещание общей задержки станка.

## Нагрузки и метод

1. **Десять разных камер**: исходные `frames36/camera_0..9/f_0000001`.
   Применены доступные тестовые ROI/настройки; физический контур есть только
   у камер 1/6. Остальные камеры проверяют ROI/весь кадр в прежнем режиме.
   Это не выгрузка активных профилей работающей машины.
2. **Десять профилей с ведром**: отдельные независимые эталоны/профили для
   десяти запросов, использующих четыре фотографии camera_1/6,
   f_0000001/396 по кругу. В каждом включена физическая компенсация.
   Это нагрузочная модель всех десяти тяжелых инспекций, не десять разных
   ракурсов машины. Новые контуры не подготавливались и в настройки
   пользователя не записывались.

Все входы смещены целиком на (1,−1) px. Настройки: чувствительность 0,5,
порог 0,6, ослабление 3 px, min_blob_area 20, допуски 4 мм с прежними
приблизительными масштабами. Все замеренные кадры прошли без брака.
OpenCV один поток, MSVC Release, одинаковые данные и зависимости.
Каждый профиль имеет собственный Reference; старты запросов параллельны,
реальная конкурентность ограничена штатными `InspectionSlots`.

Первый пакет отдельно записан как холодный и исключён из медианы/p95.
Начальный скрининг: 1/2/4/8 слотов, масштабы 50%/100%, пять повторов.
После оптимизации повторены три слота на разных камерах (12 пакетов
на масштаб/версию), шесть на нагрузочной модели (12 до, 20 после).
Первые короткие пробы и окончательные повторы хранятся отдельно;
для выводов используются окончательные повторы.

## Где тратилось время

В нагрузочной модели с одним слотом средняя native-инспекция кадра до
изменений занимала примерно 134 мс на 50% и 189 мс на 100%. Большая часть —
`align_ms`: оценка движения ведра/этикетки, маски и выравнивание изображения.
В диагностической копии отдельно измерено: движение ведра около 12 мс,
положение рисунка около 64–65 мс (два ECC-старта, около 59–61 мс суммарно),
маска/подготовка эталона 22–38 мс, выборка выровненных изображений 38–44 мс.
Диагностические пробы отдельные, поэтому суммы не подменяют пакетный замер.

Первый скрининг с компенсацией на всех десяти профилях превысил 500 мс
даже на восьми слотах: около 519 мс на 50%, около 697 мс на 100%.
Один последовательный слот для десяти разных камер дал около 902/1198 мс;
суммировать прошлые одиночные замеры как задержку параллельного пакета нельзя.

## Изменения

В `inspector.cpp` удалена лишняя подготовка изображения эталона и весов
для ветки, где `alignRoiInspectionGray` сразу пересчитывает их на
восстановленной поддержке и заменяет промежуточное изображение.
При почти нулевом сдвиге прежняя подготовка остаётся. Matcher дообучения
получает фактическое изображение `comparisonReference`, как и раньше.

В `preprocessing.h` преобразования ограничены прямоугольником, содержащим
всю ненулевую поддержку и запас для интерполяции/размытия. Соответствующие
пиксели текущего изображения берутся из полного кадра, включая выход за
старый ROI. Результат восстанавливается в прежнем размере изображения.
Проверяемая маска и запас 1 px сохранены. Размеры окна кратны целочисленному
коэффициенту уменьшения, чтобы сохранить точную сетку resize. На произвольных
и округлённых масштабах остаётся полный путь. Позиционирование ECC512,
порог, чувствительность, ослабление, score и допуски не изменялись.

Сохранён явный dense-путь для регрессионного сравнения. Новая C++ регрессия
сравнивает оба изображения (текущее и эталон) попиксельно, включая отверстия,
края кадра, узкую и полную маску, цвет/монохром, дробные сдвиги и округлённые
масштабы. После расширения на обычный ROI проверены оба вида поддержки:
**1120/1120** сравнений дают точное равенство и не меняют исходную маску.

## HTTP/SHM и регрессии

Для окончательной версии выполнены три отдельных запуска каждой версии,
порядок чередовался; по 12 измеряемых пакетов на масштаб/запуск после
прогрева. **36 пакетов на каждую строку таблицы**. Сервис использовал три
слота, клиент — десять параллельных HTTP запросов `/inspect-shm` с
постоянными соединениями. Загрузка эталонов и сохранение профилей вне
измеряемого интервала; от отправки всех запросов до разбора десяти JSON
ответов учитываются HTTP, очередь, чтение SHM и весь native проход.

|---|---:|---:|
| 50% | 388,5 / 487,7 / 491,9 | **306,0 / 366,9 / 410,9** |
| 100% | 464,6 / 550,7 / 579,9 | **396,7 / 483,7 / 491,5** |

Все **72 итоговых HTTP пакета после оптимизации** уложились в 500 мс.
Это результат данного локального прогона, не гарантия времени линии.
В нативных нагрузочных тестах выше остались пики до 534,5 мс.

До расширения оптимизации на обычные ROI HTTP на 100% всё ещё давал
p95 около 561 мс. Эти промежуточные результаты (`http-results-0/1/2.json`)
сохранены отдельно. Итоговая таблица использует исключительно
`http-results-3/4/5.json` и `final-summary.json`; их нельзя смешивать.
Расширение применено только после 1120 точных сравнений двух путей.

Штатная Release-сборка сервиса прошла. Полный CTest окончательного кода
**20/20**, включая нормы/их кэш, позицию, шов, ROI за пределами старой
рамки и новую регрессию окна. Для первой версии оптимизации физического
режима **3040 синтетических + 600 фото-инспекций** совпали с исходной
comp+ по score, причине, сдвигам и диагностике. Для окончательного
расширения отдельно повторены все **600 фото-инспекций**: изменений
результатов нет; 3040 синтетических повторно не запускались, поскольку
их ветка с уже подготовленной поддержкой не менялась. Проверка
1120 сравнений охватывает и новую ветку обычного ROI.

В `comp+` перенесены `inspector.cpp`, `preprocessing.h`, CMake-регистрация
и `preprocessing_window_test.cpp`. Исходные файлы сохранены в рабочем
каталоге проверки. Число ECC-стартов и размер ECC512 сохранены. CPU-слоты,
Linux-affinity, пользовательские картинки, профили, нормы, runtime,
ветка, Git index и commit/push не изменялись. Для работы изменений нужно
пересобрать C++ сервис обычным способом проекта.
