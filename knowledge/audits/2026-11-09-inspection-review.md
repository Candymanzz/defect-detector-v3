## 1. P1 — неизвестный успешный ответ означает ACCEPT

`orchestrator-java/.../clientapi/CppAnalisSurfaceHttpSupervisor.java:507–510`;
`.../pipeline/decision/DefaultInspectionDecisionAggregator.java:37–48`.
Клиент исключает несколько отрицательных статусов вместо явной проверки
положительного статуса. При HTTP 200 с пустым телом, `{}` или
`{"status":"UNKNOWN"}` получается `ok=true`; с geometry=SKIPPED итог ACCEPT.
Контроли ERROR/БРАК дают REJECT, ГОДЕН — ACCEPT.

Свежая проба использует настоящие текущие Java-клиент и агрегатор и локальный
HTTP mock. Это ошибка контракта при некорректном успешном ответе, а не
утверждение, что обычный C++ endpoint всегда возвращает UNKNOWN. Сетевые
ошибки этой пробой не подменялись. Нужен явный положительный контракт.

## 2. P1 — полный провал захвата оставляет цикл без результата

`.../pipeline/bucket/BucketInspectionAggregator.java:216,228`;
`.../pipeline/session/ProductionInspectionOrchestrator.java:229–244`.
Состояние bucket и таймер возникают только после первого результата.
Если не получен ни один кадр, ошибкам capture не соответствует итоговый
отказ по изделию. Свежая проба: две камеры/две группы, capture возвращает
failedFuture, failures=2, published=0, open_camera0/open_camera1=null после
ожидания 300 мс при bucket timeout 50 мс.

Контроль с одним записанным результатом создаёт состояние; тайм-аут публикует
два групповых результата, включая синтетический отказ для отсутствующей
группы. Проблема именно в полном отсутствии первого результата, а не во всех
тайм-аутах. Нужна регистрация цикла до capture либо публикация его ошибки.

## 3. P2 — включённый стык не найден, но кадр принят

`cppAnalisSurface/src/service/service.cpp:27–38` и
`cppAnalisSurface/src/core/seam.cpp:186–191`.
Решение использует `sr.reject`, но отсутствие `sr.found` не вызывает отказа.
Равномерный кадр и такой же эталон 384×320, включённая линия
[0.5,0.1]→[0.5,0.9], чувствительность 0.5:
seam_enabled=true, seam_found=false, score=0, reject=false.

Это отличается от согласованного отключения всех проверок при чувствительности
0%. Здесь проверка включена и результат измерения отсутствует. Ранее
обсуждавшееся условие `seam_not_found` в текущей ветке отсутствует.

## 4. P2 — одновременные разные ROI одной камеры меняют чужой результат

`cppAnalisSurface/src/service/service.cpp:259,277,280`.
ROI записывается в общий Reference. Запись ROI, сохранение `r.roi` и выбор
Prepared инспекции не образуют одного снимка. Mutex отдельных методов
Reference не делает всю последовательность атомарной.

Два запроса одного product с левым/правым ROI, дефект только слева:
последовательно слева score1/REJECT, справа score0/ГОДЕН. Первый свежий
конкурентный прогон 800 вызовов: 2 чужих reported ROI, 1 пропуск, 1 ложный
отказ. Второй прогон 800: 1 чужой reported ROI, 1 пропуск, 0 ложных отказов.
Это воспроизведение гонки, не оценка её производственной частоты.

Условие — разные ROI одного product/camera одновременно, например инспекция
во время изменения ROI. Разные камеры с разными scoped product этим сценарием
не затрагиваются. Нужен неизменяемый снимок ROI на запрос либо сериализация
такого изменения вместе с инспекцией.

## 5. P2 — вырожденный ROI выключает обнаружение дефекта

`cppAnalisSurface/src/service/service.cpp:198–208`;
`front-end/src/components/ReferenceSetup/referenceRoi.ts:46–48`.
Валидация не проверяет площадь/совпадение вершин. ROI из трёх одинаковых точек
(0.2,0.4) принят и даёт маску площадью 1 px. В пробе дефект 50×60 px внутри
этой области без ROI получает score1/REJECT, с вырожденным ROI — score0/ГОДЕН:
единственный пиксель отфильтрован min_blob_area=20.

Нужна геометрическая проверка ненулевой площади и корректности растровой
маски. Это не намеренное исключение дефекта корректным ROI.

## 6. P2 — неудачная запись настроек выдаётся за успех

`cppAnalisSurface/src/core/settings.cpp:286–300,324–326`.
Не проверены открытие/запись/закрытие основного и резервного ofstream.
При ошибке записи map уже изменён, set возвращает пустую строку ошибки.
Проба делает родитель `settings.json` обычным файлом: threshold=.2 сохраняется
в памяти, ошибка пустая, новый SettingsStore получает default .6.

Права/заполненный диск отдельно не имитировались, но отказ I/O воспроизведён.
Нужны проверяемая запись и согласованное состояние памяти/файла при ошибке.

## 7. P2 — повтор source/frame ID игнорирует другой образец нормы

`cppAnalisSurface/src/service/service.cpp:150–152`.
Ключ дедупликации не учитывает bbox или изображение. В **одном экземпляре
Service, без перезапуска приложения** сохранены два разных crop/bbox с
одинаковым source="50" и эталоном. Вторая операция вернула старый id и bbox
(40,50,90,90) вместо (240,180,90,90); число норм осталось 1. Второй кадр
после такого дообучения продолжает получать score1/REJECT.

Это может произойти при повторном выделении другого участка того же кадра
или при повторении frame_id после перезапуска камеры внутри работающего
приложения. Полный bootstrap-сброс норм эту коллизию внутри запуска не решает.
Отдельная первоначальная проба с перезапуском только C++ Service также
повторила коллизию; она не моделирует полный Java bootstrap, где сброс намеренен.
Нужен ключ образца с контекстом сессии/координат/контента при сохранении
идемпотентности настоящего повтора одного образца.

## 8. P2 — общий кэш эталонов скрывает старый эталон второго backend

`orchestrator-java/.../clientapi/CppAnalisSurfaceHttpSupervisor.java:340–376`.
Статический REFERENCE_SIGNATURES имеет ключ product/camera, без backend URL.
Два независимых локальных HTTP mock: B сначала получил old-reference,
A затем получил new-reference; при новой инспекции на B загрузка пропущена,
server_b_uploads=1 и B продолжает хранить old-reference.

Подтверждён пропуск нужного обновления настоящим Java-клиентом. Численная
ошибка настоящего C++ на этих двух изображениях не измерялась. Условие —
несколько backend; для одного процесса C++ эта проба не доказывает сбой.
Нужно включить конкретный backend в ключ кэша и связанные блокировки.
