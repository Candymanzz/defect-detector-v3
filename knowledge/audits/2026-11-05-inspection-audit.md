## Новые подтверждённые проблемы

### 1. P2 — обновление эталона на одном сервере скрывает старый эталон другого

`orchestrator-java/src/main/java/com/example/iml/orchestrator/integration/clientapi/CppAnalisSurfaceHttpSupervisor.java:321–350`.
`REFERENCE_SIGNATURES` статический, но ключ включает только product/camera,
без адреса или идентификатора C++-сервера. При этом каждый C++-процесс
хранит собственный Reference. `InspectPythonExecutor.java:123` выбирает
клиента round-robin, `ServicePoolLifecycle.java:179–184` поддерживает разные URL.

Проба настоящего Java-клиента с двумя независимыми HTTP mock-серверами,
каждый из которых хранит имя последнего загруженного эталона:

1. На B через inspect загружается old-reference.
2. На A для той же камеры загружается new-reference, общий cache становится new.
3. На B запрашивается инспекция с new-reference.
4. Повторная загрузка пропущена: B всё ещё хранит old-reference, uploads=1.
   `/inspect-shm` получает успех, `no_reference` не возникает, recovery не работает.

Таким образом клиент реально не отправляет требуемое обновление; численный
результат C++ на разных изображениях в этой пробе не измерялся, backend
был mock. Риск — сравнение со старым эталоном, ложное принятие/отказ.
Условие: несколько серверов. В текущем шаблоне `python_server_pool_size: 1`,
поэтому эта ошибка не объясняет обычную параллельную работу десяти камер
на одном процессе. Ключ кэша/блокировок нужен на конкретный backend+scope.

### 2. P2 — повторившийся frame_id молча отменяет новое дообучение

`cppAnalisSurface/src/service/service.cpp:150–152` возвращает существующую
запись по product_type + reference_fingerprint + source_inspection_id,
не проверяя новый crop или bbox. `source_inspection_id` в UI — строковый
`inspectResult.frame_id` (`ModalWrapper.tsx:263–264`,
`orchestratorApi.ts:505`). Backend выдаёт frame_id обычным числом,
а `camera-worker/src/main.c:2654` инициализирует next_frame_id=1 при новом
запуске. Идентификатор без сессии/контента может повториться после рестарта.

Свежая C++-проба:

- сохранён образец с source="50", bbox=(40,50,90,90);
- Service заново создан из того же dataDir, загружен прежний эталон;
- отправлен другой crop с source="50", bbox=(240,180,90,90);
- возвращён старый id и старый bbox, число образцов осталось 1;
- новый кадр после такого «дообучения» всё ещё REJECT, score=1.

HTTP route при таком возврате сообщает saved=true/accepted_count=1,
а UI показывает успешное добавление. То же происходит с пустым source,
разрешённым прямым API, хотя штатный UI обычно передаёт непустой frame_id.
Нужен устойчивый идентификатор сессии/кадра или контента crop; повторная
отправка действительно того же образца может оставаться идемпотентной.

### 3. P2 — вырожденный ROI сохраняется и выключает обнаружение крупного дефекта

`cppAnalisSurface/src/service/service.cpp:198–208` проверяет только число
точек, конечность и диапазон координат. `front-end/src/components/ReferenceSetup/referenceRoi.ts:47–49`
считает валидным любой массив из >=3 точек. Ненулевая площадь и совпадение
вершин не проверяются, поэтому UI не предотвращает передачу такого ROI.

Свежая Service-проба: дефект 50×60 px на 384×320, без ROI — score=1/REJECT.
ROI из трёх одинаковых точек (0.2,0.4) принят без ошибки, маска имеет
площадь **1 px** внутри дефекта. Из-за min_blob_area=20 отличие удалено:
score=0/ГОДЕН. Это не намеренное исключение дефекта корректным полигоном,
а принятие несуществующей области за валидно настроенную инспекцию.
Нужна проверка геометрии/площади на обеих сторонах; желательно проверять
растровую площадь и совместимость с минимальной компонентой.

## Ранее известные проблемы, повторённые на текущем коде

### 4. P1 — пустой/неизвестный успешный ответ превращается в ACCEPT

`CppAnalisSurfaceHttpSupervisor.java:483–485`,
`integration/pipeline/decision/DefaultInspectionDecisionAggregator.java:37–48`.
Клиент вычисляет ok исключением нескольких отрицательных статусов,
а не проверкой допустимого положительного ответа. Настоящий Java-клиент
и агрегатор с geometry=SKIPPED: HTTP200 с пустым телом, `{}` или
status=UNKNOWN дают ok=true и ACCEPT. Контроль ERROR/БРАК даёт REJECT,
ГОДЕН — ACCEPT. Требуется явная проверка контракта положительного ответа.

### 5. P1 — полный провал capture не создаёт deadline итогового цикла

`integration/pipeline/bucket/BucketInspectionAggregator.java:216,228`,
`integration/pipeline/session/ProductionInspectionOrchestrator.java:229–244`.
Bucket и timer создаются после первого результата, а ошибка/тайм-аут
цикла лишь журналируются. Повтор старой локальной пробы: две камеры,
две группы, capture stage возвращает failedFuture; failures=2, спустя
300 мс при bucket timeout=50 мс нет открытых bucket/результатов.
Контроль с одним вручную внесённым результатом создаёт тайм-аут и два
групповых результата. Это проверка runner/aggregator со stub-захватом;
реальный fanout/выходы ПЛК не измерялись. Регистрация ожидаемого цикла
нужна при принятии триггера, а не только после успешного capture.

### 6. P1 — включённый контроль стыка принимает его отсутствие

`cppAnalisSurface/src/service/service.cpp:38`: решение смотрит sr.reject,
но не sr.found. Ранний выход/недостаточная coverage в seam.cpp оставляют
found=false, reject=false. Равномерный кадр 384×320, такой же эталон,
включённая линия [0.5,0.1]→[0.5,0.9]: seam_enabled=true,
seam_found=false, score=0, reject=false. Проверка реально не выполнена,
а результат положительный. Ранее согласованный seam_not_found отсутствует.

### 7. P2 — разные ROI одной камеры вмешиваются друг в друга

`cppAnalisSurface/src/service/service.cpp:259,277,280`:
запись ROI в общий Reference, чтение r.roi и получение Prepared внутри
inspectFrame не образуют одного снимка запроса. Отдельные mutex методов
Reference не делают последовательность атомарной.

800 параллельных вызовов одного product с левым и правым ROI:
последовательно слева score1/REJECT, справа score0/ГОДЕН; в конкурентном
прогоне wrong_reported_roi=2, missed_defect=1, false_reject=1.
Это воспроизведение гонки, не оценка частоты на станке. Условие — разные
ROI одного product/camera одновременно, например фоновая карта и запрос
после редактирования. Разные scoped камеры этим сценарием не затрагиваются.
Нужен снимок состояния на запрос или сериализация для одного reference.

### 8. P2 — провал записи настроек выглядит как успешное сохранение

`cppAnalisSurface/src/core/settings.cpp:286–300,324–326`: не проверены
ofstream/open/write/close и резервная запись после неудачного rename.
Родитель settings.json намеренно сделан обычным файлом: set threshold=.2
возвращает пустую ошибку, в памяти .2; новый SettingsStore видит default .6.
Реальные ошибки заполненного диска/прав не имитировались, но ошибка I/O
уже воспроизведена. Нужны проверка записи и согласованное состояние
map/file при неудаче, без успешного ответа клиенту.
