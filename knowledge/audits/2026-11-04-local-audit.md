## Подтверждённые проблемы

### 1. P1 — некорректный успешный HTTP-ответ становится ACCEPT

`orchestrator-java/src/main/java/com/example/iml/orchestrator/integration/clientapi/CppAnalisSurfaceHttpSupervisor.java:483`
определяет успех исключением четырёх отрицательных статусов. Отсутствующий,
неизвестный или `null` статус не означает ошибку. `DefaultInspectionDecisionAggregator.java:41`
при пропущенной геометрии принимает это как итоговый успех.

Воспроизведение через настоящий Java HTTP-клиент с локальным mock-сервером:

| Тело HTTP 200 | ok | Итог при geometry SKIPPED |
|---|---|---|
| пустое | true | ACCEPT |
| `{}` | true | ACCEPT |
| `{"status":"UNKNOWN"}` | true | ACCEPT |
| `{"status":"ERROR"}` | false | REJECT |
| `{"status":"БРАК"}` | false | REJECT |
| `{"status":"ГОДЕН"}` | true | ACCEPT |

Это ранее известная проблема, повторно подтверждённая на текущем HEAD.
Нужно явно проверять положительный статус и обязательные поля ответа;
режим capture-only без эталона имеет отдельный контракт.

### 2. P1 — полный провал захвата цикла не запускает тайм-аут итогового результата

`BucketInspectionAggregator.java:216,228` создаёт bucket и его таймер только
после первого `recordFrameResult`. `ProductionInspectionOrchestrator.java:229`
и `:237` после ошибки/тайм-аута лишь пишут журнал. Если ни одна камера не
дала решения, bucket и sequence barrier вообще не создаются.

Локальная проба: line-broadcast на две камеры в двух группах, обе возвращают
ошибку захвата. После 300 мс при bucket timeout 50 мс: `failures=2`,
`published=0`, открытых bucket нет. Контроль: когда хотя бы один результат
поступает, барьер через тайм-аут выдаёт оба групповых результата.

Следствие: нет итогового результата именно для потерянного цикла; в hold
выходы не обновляются этим циклом. Отдельный сигнал fault/логика ПЛК может
остановить машину, но такая реакция этой локальной пробой не подтверждена.
Нужно регистрировать ожидаемый цикл и его deadline при принятии триггера,
а ошибки камер превращать в явный незавершённый/отрицательный результат.

### 3. P1 — включённый контроль стыка принимает ненайденный стык

`cppAnalisSurface/src/service/service.cpp:38` проверяет только `sr.reject`.
`core/seam.cpp` при раннем выходе или coverage < 0.5 сохраняет `found=false`
и `reject=false`. Отсутствие измерения поэтому проходит.

Воспроизведение: равномерный кадр 384×320, такой же эталон,
контроль стыка включён, линия от [0.5,0.1] до [0.5,0.9].
Результат: enabled=true, found=false, seam_reject=false, reject=false,
score=0, reason пустая. Это расходится с ранее согласованным поведением
`seam_not_found` при включённой проверке.

### 4. P2 — одинаковые изображения получают разную предобработку при уменьшении

`core/reference.cpp:40` вызывает resize с `fx/fy`, а `core/inspector.cpp:61`
передаёт округлённый размер `prep->workSize`. Если исходные размеры,
умноженные на масштаб, дробные, OpenCV использует разные коэффициенты
интерполяции. Одинаковый исходный кадр превращается в разные рабочие изображения.

На синтетическом кадре 391×325 при масштабе 0.5 максимальная разница яркости
после одинакового blur — 13 уровней. Самосравнение дало сдвиг
[0.547789, -0.778600] исходных px, response=0.884134. При приблизительном
масштабе камеры 0 это [0.428704, -0.809553] мм. С допуском 0.5 мм —
reject=true, reason=shift_exceeded, anomaly_score=0.

При допуске 0.5 мм ложный отказ также получен для ширины 384 и 612 при
масштабе 0.2. Это синтетическое воспроизведение с примерными метрическими
коэффициентами; физические миллиметры на станке им не измерены.
Нужна одна реализация resize и одинаковые размеры/коэффициенты для обоих кадров.

### 5. P2 — параллельные запросы одной камеры могут использовать чужой ROI

`service/service.cpp:259` записывает request ROI в общий Reference.
Чтение `r.roi` на :277 и получение prepared reference внутри `inspectFrame`
на :280 выполняются позже без общего снимка состояния запроса.
Мьютекс каждого отдельного метода Reference не делает эту последовательность атомарной.

Воспроизведение: один product, два worker, одновременно левый и правый ROI.
В левом находится заметный дефект; последовательные базовые результаты —
REJECT слева и ACCEPT справа. В расширенной пробе из 600 параллельных вызовов
получен один чужой ROI и один пропуск дефекта. В первоначальной пробе также
были ложные отказы правой зоны. Количество зависит от расписания потоков;
это доказательство гонки, не оценка частоты ошибок на производстве.

Условие проявления: разные ROI одного product/camera одновременно, например
старый фоновый запрос карты и запрос после редактирования ROI. Разные камеры
со своими scoped product этой пробой не затронуты. Java scope-lock защищает
загрузку эталона, а не всю инспекцию. Нужен immutable снимок ROI/prepared на
запрос или сериализация смены ROI и вычисления для одного reference.

### 6. P2 — ошибка сохранения настроек скрывается

`core/settings.cpp:286` не проверяет ошибки create_directories, открытия,
записи/закрытия временного и резервного файлов. `SettingsStore::set` меняет
map, вызывает save и возвращает пустую строку ошибки даже при провале записи.

Проба: родительский путь settings.json намеренно сделан обычным файлом.
Сохранение threshold=0.2 вернуло `error=""`; get в текущем процессе — 0.2;
после нового SettingsStore — default 0.6. UI может показать успех, хотя после
рестарта настройка потеряется. Аналогично не проверяются ошибки диска/прав;
полный диск отдельно не имитировался.
