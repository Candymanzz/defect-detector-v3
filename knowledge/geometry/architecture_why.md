# geometry — architecture "WHY"

Back to [overview](./overview.md) · Evidence tags as in other files.

1. **Separate Java/OpenCV service for geometry** ⚠️ [GUESS/CONJECTURE]: the metrics are explicit mm-tolerance measurements (Hough/fitLine/ORB), independent from the statistical, learnable surface detector; keeping them apart lets each be tuned/blamed separately. Note the orchestrator chains them **sequentially per camera** (capture → geometry → python, `AsyncInspectionCycleRunner:61-94`); parallelism is across the ten cameras, not between the two detectors.
2. **Frames by SHM descriptor, with `RandomAccessFile` + reusable buffers** **[doc]** `ShmMatReader` javadoc: `MappedByteBuffer` regions are released only by GC and RSS grew over multi-day runs.
3. **Reference LRU of 2 and a single-entry prepared-ORB cache.** **[doc]** `ReferenceShmMatCache` javadoc says “до 10 эталонов одновременно” but **[code]** `MAX_CACHED_REFERENCES = 2`; and `OpenCvGeometryAnalysisService` keeps exactly one `preparedReferenceCache` (key = `referenceCacheKey`). The orchestrator picks a geometry JVM **round-robin** (`geometryRoundRobin`), so one JVM sees many different cameras ⇒ each call can miss both caches (one SHM read + one ORB build of the reference at ≤640 px). ⚠️ [GUESS/CONJECTURE] this is a latent inefficiency (intent 10, constant 2) accepted because positioning/ORB on small images is cheap; pinning a camera to a JVM would remove it.
4. **Pose-locked mode** (`pose_locked/already_aligned`): when upstream positioning already aligned the frame, re-running ORB “often invents a residual H and destroys the lock” **[doc code comment]**; alignment becomes identity, wrinkles can't fail (“geometry absdiff wrinkles are too light-sensitive and caused false rejects on matched frames; surface QC belongs to python”). Related history: `83bb9d19` (Java positioning, 2026‑07‑14), `3df6b127` (trim, 2026‑09‑22), `9ba4efc5` (centralised in Python, 2026‑09‑30). With positioning now in Python (translation only) and `java_positioning.enabled:false`, `pose_locked` is normally **false** for geometry, so geometry still aligns itself by ORB homography.
5. **Joint-camera gating** — commit `ed636eaa` “Gate yellow-rim skew and concentricity to joint camera only” (2026‑09‑10): sibling (angled) buckets always show an optical wedge; yellow stripes on every bucket are neither needed nor reliable **[doc: code comments in `evaluateRimSkewPass`/`siblingView`]**. Siblings only report `jointVisibility` (used later by the orchestrator's strict gate).
6. **Seam: two-stage detection** (segmenter then Hough pair): the segmenter locks a weak band with sensitivity-tunable thresholds; Hough remains the fallback; a not-found seam on a joint camera is a defect (a label missing/rotated) **[code]** `evaluateJointPass`.
7. **“Inconclusive PASS” below the noise floor and min-width waiver when parallel** **[doc]** code comments (Canny double edges ≈2–4 px ≈0.04–0.08 mm at 0.02 mm/px); YAML note: working seams on the bench measure ~0.35–0.45 mm so `joint_min_width_mm 0.25`; lower cameras (viewed from below) get `max_joint_parallelism_deg 5.0` because converging edges give 2.5–3.2° on a good seam.
8. **Sensitivity scaling of parallelism** (0 → 2×, 0.5 → 1×, 1 → 0.4×): gives the operator one monotone “strictness” knob (UI Simple/Pro `joint_seam_segmentation_sensitivity`) without exposing raw degrees – ⚠️ [GUESS/CONJECTURE].
9. **Concentricity deviation ≤2 px treated as 0 and no-circle ⇒ pass**: avoids rejects from Hough instability; threshold fixed 0.2 mm (not configurable) ⚠️ [GUESS/CONJECTURE: low priority metric].
10. **Failure value 9999** for failed alignment: ensures any missing homography is a definite FAIL rather than a silent 0 mm shift **[code]** `FALLBACK_FAIL_MM`.
11. **One JVM per pool slot with 10 slots** – isolation and parallel capacity (`geometry_pool_size 10`, `geometrySlots` semaphore); JVM warm-up cost accepted ⚠️ [GUESS/CONJECTURE].

## Customer requirement recorded 2026-10-20

Geometry QC must distinguish whole-bucket image motion from label placement relative to the bucket. The customer requests flexible seam tolerance in mm (2 mm is an example), separate horizontal/vertical placement limits and geometry rejection outside those limits; displaying actual measured deviations is desired. Alignment intended to stabilise surface comparison must not hide a truly misplaced label. The [requirements note](./customer_requirements.md) records calibration, reporting and acceptance questions separately from the implemented image-alignment/seam algorithms. No implementation change is implied.
